# Promote — suíte completa e e2e em staging promovem para produção

> **TLDR**: um workflow `promote` gerado pelo render roda depois de cada deploy verde de staging, executa os hooks `regression` (suíte inteira no runner) e `e2e` (testes reais contra a Release URL daquela release) e, se os dois passam, grava o record `promoted` e dispara o deploy de produção. Na falha abre uma Critical issue. O PR passa a receber `BASE_SHA` para rodar só o que mudou.

# what

    Como dono de um projeto br4zz4/pipelines (o lunetamagica primeiro), quero que toda release
    verde em staging seja provada pela suíte completa e por testes reais no ambiente no ar e,
    se passar, vá sozinha para produção, para entregar rápido sem promover à mão e sem que um
    bug chegue a produção sem virar uma Critical issue.

Glossário: `docs/CONTEXT.md` (**Promote**, **Regression**, **E2E**, **Release URL**, **Critical issue**, Release tag, Record, Deploy, Hook, Render, Conform).

Esta é a spec 1 de 3. A spec 2 (`docs/specs/20261121100100_autofix_critical_issues.md`) consome as Critical issues que esta abre. A spec 3 (dependabot automático) vem depois.

## Modelo

### Configuração (`.github/modules.json`)

```json
{
  "promote": { "max_per_day": 10 }
}
```

| chave | obrigatória | default | regra |
|---|---|---|---|
| `promote` | não | ausente | objeto; ausente = nada muda no projeto (promoção continua manual) |
| `promote.max_per_day` | não | ausente = sem limite | inteiro ≥ 1 |

Chave desconhecida dentro de `promote` é erro de render. No lunetamagica: `"promote": {}`.

### Hooks novos (lado code, vocabulário fechado)

| hook | onde | job | ward environment | recebe |
|---|---|---|---|---|
| `regression` | `run/regression` ou `ci/checks/regression.sh` | `promote / regression` | `test` (mesmos escopos do `test` do `code.yml`), com os `services` do módulo | `MODULE`, `ENVIRONMENT=test`, `TAG`, `CI_CACHE_DIR` |
| `e2e` | `run/e2e` ou `ci/checks/e2e.sh` | `promote / e2e` | `staging` (`<ns>:secrets.ci.staging` e `<ns>:secrets.<m>.code.staging`), sem `services` | `MODULE`, `ENVIRONMENT=staging`, `TAG`, `TARGET_URL`, `CI_CACHE_DIR` |

- O conform só exige os dois quando a chave `promote` existe. Sem a chave, ausentes não reprovam (mudança aditiva dentro da `v1`).
- Os testes de e2e de um módulo moram em `<code_dir>/e2e/`, nunca em `test/`. É um caminho que o pipeline conhece (a spec 2 o proíbe ao agente) e fica fora do `bin/rails test` padrão.
- Na falha, o hook pode escrever `<code_dir>/tmp/artifacts/failures.md` (nome dos testes, asserção e stack, sem segredo). O `tmp/artifacts/` existe só no runner, nunca no repositório.

### `BASE_SHA` no `test`

No `pull_request`, o job `test` do `code.yml` faz checkout com `fetch-depth: 0` e exporta `BASE_SHA=$(git merge-base <github.event.pull_request.base.sha> HEAD)` para o hook. Em `main` e em dispatch, `BASE_SHA` é vazio (o hook roda tudo). O projeto decide o que é "impactado". A seleção inteligente fica na issue br4zz4/pipelines#16.

### Release URL

- O hook `verify` pode escrever `release_url=<url>` em `$GITHUB_OUTPUT` além de `url=`. A step expõe o output, o job `verify` do `deploy.yml` o publica e o `record` o grava no payload da Deployment: `{"module", "tag", "release_url"}`.
- Com `promote` ligado, o staging **precisa** ter `release_url`. Sem ela o `target` falha com `::error::verify wrote no release_url for <tag>` e nada é promovido. Um provedor sem URL presa à release escreve a URL padrão do ambiente (decisão do script do projeto).

### Workflow gerado no projeto (`.github/workflows/promote.yml`)

Escrito pelo render só quando a chave `promote` existe. O conform o trata como parte do padrão.

```yaml
# generated by br4zz4/pipelines render — do not edit
name: promote
run-name: promote · ${{ github.event.workflow_run.head_branch || inputs.tag }}
on:
  workflow_run:
    workflows: [ deploy ]
    types: [ completed ]
  workflow_dispatch:
    inputs:
      tag:
        description: Release tag to promote
        required: true
        type: string
permissions:
  contents: read
  id-token: write
  actions: write
  deployments: write
  pull-requests: read
jobs:
  conform:
    # mesmo job conform (mode: check) dos outros workflows gerados
  target:
    name: target
    needs: conform
    if: ${{ github.event_name == 'workflow_dispatch' || (github.event.workflow_run.event == 'push' && github.event.workflow_run.conclusion == 'success') }}
    # action promote (command: target) com o JSON de módulos; outputs module, tag, code_dir, services, release_url
  incident:
    name: incident
    needs: conform
    if: ${{ github.event_name == 'workflow_run' && github.event.workflow_run.event == 'workflow_dispatch' && github.event.workflow_run.conclusion == 'failure' && startsWith(github.event.workflow_run.display_title, 'production') }}
    # action critical (command: incident): Critical issue com autofix:blocked
  promote:
    name: promote
    needs: target
    concurrency:
      group: promote-${{ needs.target.outputs.module }}
      cancel-in-progress: true
    uses: br4zz4/pipelines/.github/workflows/promote.yml@v1
    with:
      module: ${{ needs.target.outputs.module }}
      vault: lunetamagica
      tag: ${{ needs.target.outputs.tag }}
      code_dir: ${{ needs.target.outputs.code_dir }}
      services: ${{ needs.target.outputs.services }}
      release_url: ${{ needs.target.outputs.release_url }}
      max_per_day: 0
    secrets:
      WARD_KEY: ${{ secrets.WARD_KEY_LUNETAMAGICA }}
```

`max_per_day: 0` significa sem limite. O `deploy.yml` gerado ganha, só com a chave `promote`, o input de dispatch `force` (boolean, default `false`) e passa `require_promoted: ${{ !inputs.force }}` ao reusable.

### Reusable `promote.yml`

```
regression ∥ e2e ─┬─► promote (superseded? capped? → record promoted → dispatch produção) ─┐
                  └─► report (falha → Critical issue) ─────────────────────────────────────┴─► notify
```

| job | secrets que vê | o que faz |
|---|---|---|
| `regression` | escopos de `test` | hook `regression` com os `services`; `timeout-minutes: 60`; na falha publica `tmp/artifacts` como `failures-regression` |
| `e2e` | escopos de `staging` | hook `e2e` com `TARGET_URL=<release_url>`; `timeout-minutes: 30`; na falha publica `failures-e2e` |
| `promote` | `GITHUB_TOKEN` (`deployments: write`, `actions: write`) | só se os dois passaram; action `promote` (command: `decide`) |
| `report` | `<ns>:secrets.ci.common` (`GH_PIPELINES_TOKEN`) | só se `regression` ou `e2e` falhou; action `critical` (command: `open`) |
| `notify` | `<ns>:secrets.ci.common` | `if: always()`; status `promoted`, `superseded`, `capped` ou `failed` |

Todos com `persist-credentials: false`. Nenhum job usa `environment:`.

### Decisão do `promote` (ordem; a primeira que casar encerra)

1. **superseded (staging):** a última tag gravada verde em staging para o módulo (`resolve` sem tag) não é a tag do run → `superseded`.
2. **superseded (produção):** a tag verde mais recente do módulo em produção é mais nova que a do run (compara `(data, int(NNN))`) → `superseded`.
3. **capped:** `max_per_day > 0` e o número de Deployments `promoted` do projeto criados nas últimas 24h é `>= max_per_day` → `capped`, com `promote capped (<n>/<max>)` no summary.
4. **promoted:** grava a Deployment `environment: promoted` com `state: success` (action `record`) e roda `gh workflow run deploy.yml --ref <tag> -f environment=production` com o `GITHUB_TOKEN`.

O `preflight` de produção do `deploy.yml`, quando `require_promoted` é `true`, resolve a tag em `promoted` em vez de `staging` (mesmo `resolve`, mesmo `staging_wait`). Com `force: true` volta a exigir só o record de staging e o summary registra `forced: promote skipped`.

### Critical issue aberta pelo pipeline (action `critical`)

- Título: `bug: <module> <regression|e2e> failed on <tag>`.
- Corpo: link do run, hook, tag, e o `failures.md` do artifact. O `failures.md` passa por máscaras (e-mail → `<email>`, IPv4/IPv6 → `<ip>`, `[A-Za-z0-9_\-]{32,}` → `<token>`) e é truncado em 20 000 caracteres. Sem `failures.md`: `no failures.md was written; see the run`.
- Labels: `urgency:critical` e `module:<m>` (criadas com `--force` se faltarem). Sempre `module:<m>`, mesmo em projeto de um módulo.
- **Dedup:** existe Critical issue aberta cujo título começa com `bug: <module> <hook> failed on ` → comenta o corpo novo nela, sem abrir outra.
- **`autofix:blocked`:** algum PR mergeado entre a última tag `promoted` do módulo e a tag do run tem a label `autofix` (`gh api repos/{repo}/compare/{base}...{tag}` e `commits/{sha}/pulls`) → a issue ganha também `autofix:blocked`. Sem tag `promoted` anterior, não marca.
- **Incidente de produção** (job `incident`): um deploy de produção que falhou abre `bug: <module> production deploy failed on <tag>` com `urgency:critical`, `module:<m>` e sempre `autofix:blocked` (o agente não mexe em infra). O módulo vem do prefixo da tag do `head_branch`.
- Aberta com `GH_PIPELINES_TOKEN`, para que o evento `labeled` dispare workflows (o da spec 2).

## out of scope

- O Autofix (spec 2) e o dependabot automático (spec 3).
- Seleção de testes por impacto além do `BASE_SHA` (issue br4zz4/pipelines#16).
- Release URL de verdade no lunetamagica: Cloud Run com tag não serve o tenant por subdomínio e o `config.hosts` bloqueia `*.run.app`. O luneta escreve a URL padrão de staging; a URL presa por release fica numa issue `urgency:normal` no lunetamagica.
- Rollback por redeploy de tag (spec de outro agente): é um `workflow_dispatch` e o `promote` o ignora.
- Limpeza das tags de revisão antigas no provedor: responsabilidade do `rollout` de cada projeto.
- Rollback de staging quando o e2e falha: staging fica mostrando o bug.
- Revisor humano ou required reviewers no environment `production` (precisa estar desligado para a promoção ser automática; documentado).
- Windows.

## acceptance criteria

    Cenário: release verde em staging vai para produção
      Dado o lunetamagica com "promote": {} e o deploy de staging de core.2026-11-21.001 terminado com success
      Quando o workflow_run dispara o promote
      Então regression e e2e rodam em paralelo, e2e com TARGET_URL igual à release_url do record de staging
      E existe uma Deployment "promoted" de core.2026-11-21.001
      E um run do deploy em produção na ref core.2026-11-21.001 foi criado
      E o notify envia "promoted"

    Cenário alternativo: deploy de staging falhou ou foi um dispatch
      Dado um run do deploy com conclusion failure, ou com event workflow_dispatch em staging
      Quando o workflow_run dispara o promote
      Então target é pulado e não há promote, report nem notify

    Cenário alternativo: regression falha
      Dado um teste quebrado na suíte do core
      Quando o promote roda
      Então promote é pulado e nenhum deploy de produção é criado
      E existe a issue "bug: core regression failed on <tag>" com urgency:critical e module:core
      E o notify envia "failed"

    Cenário alternativo: falha repetida
      Dado uma Critical issue aberta "bug: core e2e failed on core.2026-11-21.001"
      Quando o e2e de core.2026-11-21.002 falha
      Então a issue existente recebe um comentário e nenhuma issue nova é aberta

    Cenário alternativo: falha depois de um PR do autofix
      Dado um PR com label autofix mergeado entre a última tag promoted do core e a tag do run
      Quando o e2e falha
      Então a Critical issue sai com as labels urgency:critical, module:core e autofix:blocked

    Cenário: segredo não vaza para a issue
      Dado um failures.md com um e-mail, um IP e um token de 40 caracteres, e 30 000 caracteres
      Quando a action critical monta o corpo
      Então aparecem "<email>", "<ip>" e "<token>" e o trecho do failures.md tem no máximo 20 000 caracteres

    Cenário alternativo: staging sem release_url
      Dado um record de staging sem release_url no payload
      Quando o target roda
      Então ele falha com "verify wrote no release_url for <tag>" e nenhuma issue é aberta

    Cenário alternativo: release superada em staging
      Dado que core.…002 ficou verde em staging enquanto o promote de core.…001 terminava
      Quando o job promote decide
      Então o desfecho é "superseded" e nada vai para produção

    Cenário alternativo: produção já tem release mais nova
      Dado produção verde em core.2026-11-21.010 e o promote de core.2026-11-21.009
      Então o desfecho é "superseded" (010 > 009, comparando NNN como inteiro)

    Cenário alternativo: promotes sobrepostos
      Dado um promote de core em andamento
      Quando outro promote de core começa
      Então o primeiro é cancelado, e um promote de outro módulo segue em paralelo

    Cenário alternativo: teto diário
      Dado max_per_day 2 e duas Deployments promoted nas últimas 24h
      Quando o promote decide
      Então o desfecho é "capped" e o summary mostra "promote capped (2/2)"

    Cenário alternativo: produção sem passar pelo promote
      Dado um dispatch do deploy em produção numa tag sem record promoted
      Então o preflight falha com "<tag> is not recorded green in promoted"
      E com force true o preflight aceita o record de staging e o summary mostra "forced: promote skipped"

    Cenário alternativo: deploy de produção falha
      Dado o deploy de produção de core.…001 disparado pelo promote terminando em failure
      Então existe a issue "bug: core production deploy failed on core.…001" com autofix:blocked

    Cenário: PR recebe BASE_SHA
      Dado um pull request
      Quando o job core / code / test roda
      Então o hook recebe BASE_SHA igual ao merge-base com a base, e em main o recebe vazio

    Cenário: render com promote
      Dado um modules.json com "promote": {"max_per_day": 10}
      Quando rodo render.py
      Então ele escreve promote.yml com o JSON de módulos e max_per_day 10, e o deploy.yml ganha o input force
      E sem a chave promote os quatro fixtures existentes renderizam byte a byte iguais

    Cenário alternativo: configuração inválida
      Dado "promote": {"max_per_day": 0} ou uma chave desconhecida em promote
      Então render.py falha citando a chave

    Cenário alternativo: hooks ausentes
      Dado a chave promote e um módulo sem run/e2e nem ci/checks/e2e.sh
      Quando roda o conform
      Então ele reprova citando o hook e2e; sem a chave promote, não reprova

    Cenário: plataforma
      Dado macOS e Linux
      Quando rodo tests/promote, tests/critical, tests/render, tests/conform e tests/actions
      Então a saída é idêntica nos dois

    Cenário: lunetamagica promovido de ponta a ponta
      Dado o lunetamagica com os 5 e2e, a escola e2e provisionada e "promote": {}
      Quando um merge na main gera uma release tag
      Então staging sobe, regression e e2e passam e a mesma tag fica verde em produção sem dispatch manual

# why

Hoje produção só sobe quando alguém dispara o deploy à mão numa tag verde de staging, e o único teste depois do deploy é o `/up` do `verify`. Uma release pode quebrar o fluxo de matrícula em staging, ficar verde, e ser promovida assim. Ao mesmo tempo, a regra "PR roda a suíte inteira" deixa o PR lento. Esta spec move a prova pesada para depois do staging: o PR roda só o impactado, e a release só chega a produção depois da suíte inteira e de testes reais no ambiente no ar. Toda falha vira uma Critical issue com o diagnóstico, que a spec 2 transforma em correção automática. Isso fecha o ciclo "bug → issue → fix → release → prova → produção" sem humano no caminho feliz e com um humano chamado (`autofix:blocked`) quando um conserto automático quebra de novo.

# how

TDD em toda task de código: o tester escreve o teste vermelho a partir dos cenários, o builder implementa o mínimo e a suíte fica verde. Validação padrão do repo: `python3 -m py_compile actions/*/*.py tasks/check.py && python3 tasks/check.py && sh tasks/check_rendered.sh && for t in tests/*/run.sh; do sh "$t" || exit 1; done && shellcheck -S warning actions/*/*.sh examples/*/*/ci/**/*.sh tests/*/run.sh tasks/*.sh`.

**Feature flag:** sem Flipper. A ativação é a chave `promote` no `modules.json`, por projeto. Sem ela, os workflows renderizam byte a byte iguais.

**Telas:** sem telas criadas ou editadas (pipelines e hooks de CI; os e2e só leem telas existentes).

**Tag `v2`** (a major vigente da `main`; onde esta spec diz `v1`, leia `v2`): os PRs 1–7 entram no `main` do pipelines sem mover a `v2`. Só o PR 11 move.
