# v2 — main só divide, build por módulo e rollback como deploy

> **TLDR**: na `v2` do pipelines o `main.yml` não tem mais trilhas: o job `split` empurra uma build tag `build/<release tag>` por módulo alterado, e cada uma dispara um run do `build.yml` (checks com reuse desde a última release, imagem e release tag, que segue disparando o staging). O hook `rollback` some: um deploy que falha dispara um deploy da última release verde, pelo mesmo track. `main`, `build` e `deploy` gerados deixam de depender dos módulos.

# what

    Como dono de um projeto br4zz4/pipelines (o lunetamagica primeiro), quero que os workflows
    gerados não dependam dos módulos, que cada módulo construa a sua release num run próprio e
    em ordem, e que o rollback passe pelas mesmas etapas de um deploy, para ter configuração
    igual em todo projeto, releases que nunca voltam no tempo e um rollback tão provado quanto
    o deploy.

Glossário: `docs/CONTEXT.md` (**Track**, **Split**, **Build tag**, **Build**, **Release tag**, **Deploy**, **Rollback**, Module, Hook, Render, Conform, Record).

Esta spec vem **antes** de `20261121100000_promote_staging_to_production.md` e `20261121100100_autofix_critical_issues.md`, que serão revistas para a `v2` (ver "Impacto nas specs seguintes").

## Modelo

### Fluxo

```
push main ─► main:  conform ∥ detect ─► split ──push build/core.2026-11-21.001──┐
                                                                               ▼
build/core.…001 ─► build: conform ∥ target ─► build / reuse ─┬─► build / code  : lint ∥ audit ∥ test ─┬─► build / image ─► build / release
                                                             └─► build / infra : validate ∥ plan     ┘        (push core.…001, apaga build/core.…001)
                                                                                                                         ▼
core.…001 ─► deploy: conform ∥ release-start ─► deploy: preflight ─► apply ─► deployment ∥ migrate ─► rollout ─► verify ─┬─► record ─┐
                                                                                                                       └─► rollback ┴─► notify
                                                                                                    (rollback = gh workflow run deploy.yml --ref core.…001 -f rollback_to=<P>)
```

### `main.yml` gerado

- Jobs `conform` (check) ∥ `detect`, depois `split` (`needs: [ conform, detect ]`). Nenhum job por módulo.
- `split` (action `split`): para cada módulo com `changes.<m>.any`, em ordem alfabética, calcula o nome com a lógica da action `tag` e empurra a tag anotada `build/<nome>` (mensagem `build <nome>`) **sem `--force`**, com `GH_PIPELINES_TOKEN` (escopo `<ns>:secrets.ci.common`). Push rejeitado porque a tag já existe → NNN seguinte, até 5 tentativas. Falha num módulo não para os outros; o job reprova no fim listando os módulos que falharam. Nenhum módulo alterado → `nothing to build` no summary e sucesso.
- `main.yml` continua **sem** `concurrency` (um run pendente cancelado perderia o `before..HEAD` dele).
- Permissões: `contents: read`, `id-token: write`.

### Action `tag`

Passa a contar `build/<prefix>.<dia>.*` e `<prefix>.<dia>.*` ao escolher o NNN, e o laço do `ls-remote` checa as duas formas. Assim um build em andamento reserva o nome.

### `build.yml` gerado

```yaml
# generated by br4zz4/pipelines render — do not edit
name: build
run-name: ${{ github.ref_name }}
on:
  push:
    tags: [ 'build/**' ]
permissions:
  contents: read
  id-token: write
  checks: read
  pull-requests: read
jobs:
  conform:
    # mesmo job conform (mode: check)
  target:
    name: target
    # action target: outputs module, tag, code_dir, infra_dir, services, code, infra
  build:
    name: build
    needs: [ conform, target ]
    concurrency:
      group: build-${{ needs.target.outputs.module }}
      cancel-in-progress: true
    uses: br4zz4/pipelines/.github/workflows/build.yml@v2
    with:
      module: ${{ needs.target.outputs.module }}
      vault: <ns>
      tag: ${{ needs.target.outputs.tag }}
      code_dir: ${{ needs.target.outputs.code_dir }}
      infra_dir: ${{ needs.target.outputs.infra_dir }}
      services: ${{ needs.target.outputs.services }}
      code: ${{ needs.target.outputs.code }}
      infra: ${{ needs.target.outputs.infra }}
    secrets:
      WARD_KEY: ${{ secrets.WARD_KEY_<NS> }}
```

A concurrency fica no job porque uma expressão de workflow não consegue extrair o módulo da ref. `cancel-in-progress: true`: o build mais novo de um módulo cancela o anterior (a `main` é linear e o detect desde a última release cobre a mudança cancelada). A build tag de um run cancelado fica.

### Action `target`

- Lê `github.ref_name`; exige a forma `build/<module>.YYYY-MM-DD.NNN` (`::error::invalid build tag '<ref>' (expected build/<module>.YYYY-MM-DD.NNN)`) e o módulo no `modules.json` (`::error::build tag <ref> names module <m>, which is not in .github/modules.json`).
- `tag` = a ref sem `build/`; `code_dir`, `infra_dir` (defaults `modules/<m>/code|infra`) e `services` (csv) do `modules.json`.
- **Última release:** a release tag `<m>.YYYY-MM-DD.NNN` mais nova por `(data, int(NNN))` que é ancestral do commit (`git merge-base --is-ancestor`). Com ela, `code` e `infra` vêm do `detect` no intervalo `última release..commit` (mesmo mecanismo do `apply-needed`); sem ela, ou em qualquer erro, os dois são `true`. Escreve `last release: <tag|none>; code=<b> infra=<b>` no summary.

### Reusable `build.yml`

| job | `if` | o que faz |
|---|---|---|
| `reuse` | sempre | `reuse-code` e `reuse-infra` com `check_prefix: <m> / code` e `<m> / infra` (os nomes do `pr.yml`, que não muda) |
| `code` | `inputs.code == 'true'` | chama `code.yml` com `skip_<check>` do `reuse` |
| `infra` | `inputs.infra == 'true'` | chama `infra.yml` com `skip_<check>` do `reuse` |
| `image` | `!failure() && !cancelled() && needs.reuse.result == 'success'` | hook `build` (lado code, `environment: staging`, escopo `<ns>:secrets.<m>.infra.staging`) com `TAG` |
| `release` | `image` success | `stamp` empurra a release tag e apaga `build/<tag>` no remote |

No grafo: `build / reuse`, `build / code / lint`, `build / image`, `build / release`. A release tag continua existindo só se a imagem existe.

### `deploy.yml` gerado

- Dispatch ganha o input `rollback_to` (string, default `''`, descrição `Release to roll back to; set by a failed deploy`).
- `run-name`: `<env> · rollback · <P> (from <X>)` quando `rollback_to` está preenchido; senão o de hoje (`<env> · <tag>`).
- Permissões ganham `actions: write` (dispatch do rollback e leitura dos runs na fila).
- `release-start` (action `releases`) ganha os outputs `code_dir`, `infra_dir` (do `modules.json`, corrigindo o `modules/<m>/code` fixo de hoje) e `rollback_of`; o job `deploy` passa `tag`, `code_dir`, `infra_dir` e `rollback_of` desses outputs.

### Action `releases` com `rollback_to`

Em `workflow_dispatch` numa tag com `rollback_to` preenchido: `rollback_to` precisa ter a forma de release tag e o mesmo módulo da ref (`::error::rollback_to <P> is not a release of <m>`); `tag=<P>` e `rollback_of=<ref>`. Em `push` de tag, `rollback_to` é ignorado e `rollback_of` sai vazio.

### Reusable `deploy.yml`

- Input `rollback_of` (string, default `''`).
- `preflight`: com `rollback_of`, `requirements` roda com `strict: false` (P não é o commit do run, que é X) e um step `rollback target` (action `resolve`, `environment: inputs.environment`, `tag: inputs.tag`, `wait: 0`) exige P gravada verde no ambiente. `apply-needed` ganha o input `force` e recebe `force: true` no rollback.
- O job `rollback` passa a ser: `if: always() && inputs.rollback_of == '' && (deployment|migrate|rollout|verify == 'failure')`, `permissions: { actions: write }`, action `rollback` com `environment`, `module`, `tag`, `previous` (`needs.preflight.outputs.previous`) e `token: ${{ github.token }}`; outputs `status` e `target`.
- Ação `rollback`, em ordem:
  1. `previous` vazio ou igual a `tag` → `status=none`, `no earlier release to roll back to`.
  2. Algum run do `deploy.yml` com status `queued`, `pending`, `waiting` ou `requested` e `displayTitle` começando por `<env> · <module>.` → `status=skipped`, `rollback skipped: <Y> is queued`.
  3. Senão `gh workflow run deploy.yml --ref <tag> -f environment=<env> -f rollback_to=<previous>` → `status=dispatched`, `target=<previous>`. Erro do `gh` → o job falha.
- O workflow executado é o da ref X (formato atual, já conformado); o conteúdo deployado é P, porque todo job faz checkout de `inputs.tag`.
- `notify` ganha o input `detail`, anexado à mensagem:
  - run normal com `verify` verde → `ok`;
  - run normal com falha → `failed`, com `detail` `rolling back to <P>`, `rollback skipped: <Y> is queued` ou `no earlier release to roll back to`;
  - run de rollback com `verify` verde → `rolled back` com `detail` `<P> after <X> failed`; com falha → `failed` com `detail` `rollback of <X> failed`.
- Saem do reusable: o job `rollback` antigo (hook `rollback` + `verify`), o output `rollback` do `deployment` e o `rollback-point`.

### Fim do hook `rollback`

- `rollback` sai do vocabulário de `deploy` (`hook.sh`, `conform.py`); `ROLLBACK_POINT`, o input `rollback-point` da `step` e o output `rollback` da `hook`/`step` deixam de existir; o `deployment` não escreve mais `rollback=`.
- O conform reprova `ci/deploy/rollback.sh` com `rollback.sh is retired in v2: a failed deploy dispatches a deploy of the previous release`.
- `examples/`: apagar os quatro `rollback.sh`, tirar o `rollback=` dos `deployment.sh` e `rollback` das descrições de `step` nos `setup-action.yml`.

### `v2`

- Referências internas `@v1` → `@v2` (workflows, actions, `DEFAULT_REF` do render, README, contrato). `tasks/release.sh` reescreve `@v[0-9]+` em vez de `@v1` para pré-releases.
- A `v1` fica congelada no commit atual, sem branch de manutenção. Um dispatch de uma tag anterior à migração roda o `deploy.yml` daquela tag (`@v1`) e passa no conform da `v1`.
- A tag `v2` é criada depois do merge do último PR deste repo (`sh tasks/release.sh v2 --push`).

### Impacto nas specs seguintes (para a revisão delas)

- **Promote:** mirar `v2`; o PR 2 dela (release_url, `require_promoted`) muda o `deploy.yml` novo (com `rollback_of`); o `workflow_run` com `event == 'push'` já ignora runs de rollback (são dispatch); o `incident` casa `production · rollback · …` pelo `display_title`; o `promote.yml` gerado deve ler o módulo em runtime (como o `target`) em vez de embutir o JSON de módulos; uma falha de produção agora dispara rollback automático, e a Critical issue pode citar o desfecho.
- **Autofix:** mirar `v2`; o JSON de módulos embutido no `autofix.yml` deve virar leitura em runtime; o automerge aumenta o ritmo de merges, coberto pela concurrency do build.

## out of scope

- `pr.yml`: continua com trilhas por módulo e o gate `check/pr`.
- Rebuild automático de um módulo cujo build falhou: o `split` só olha `before..HEAD`; o próximo push que tocar o módulo checa desde a última release.
- `workflow_dispatch` no `build.yml`: re-tentar é "Re-run" no run da build tag.
- Concurrency configurável no `modules.json`.
- Manutenção da `v1` depois da `v2`.
- Migração do has_warranty: issue aberta nesta spec, executada depois.
- Rollback quando o `apply` falha (nada foi ao ar) e rollback de migrations (o rollback roda o `migrate` de P, que não desfaz schema).
- Windows.

## acceptance criteria

    Cenário: main divide por módulo
      Dado um push na main que altera modules/core/code e modules/gateway/infra
      Quando o main roda
      Então o split empurra build/core.2026-11-21.001 e build/gateway.2026-11-21.001, nessa ordem
      E o main não tem nenhum job por módulo

    Cenário alternativo: nada a construir
      Dado um push que só altera docs/x.md
      Quando o main roda
      Então o split termina com sucesso e "nothing to build" no summary

    Cenário alternativo: nome já reservado
      Dado build/core.2026-11-21.001 já no remote e sem release core.2026-11-21.001
      Quando o split calcula o nome de core
      Então ele empurra build/core.2026-11-21.002

    Cenário alternativo: push de um módulo falha
      Dado o push de build/core.… rejeitado 5 vezes
      Quando o split roda para core e gateway
      Então build/gateway.… é empurrada e o job reprova citando core

    Cenário: build checa desde a última release e publica
      Dado core.2026-11-20.004 como última release ancestral e o intervalo alterando só modules/core/code
      Quando build/core.2026-11-21.001 é empurrada
      Então target sai com code=true e infra=false
      E build / infra é pulado, build / code roda o que o reuse não provou
      E build / image recebe TAG=core.2026-11-21.001
      E a release tag core.2026-11-21.001 é empurrada e build/core.2026-11-21.001 é apagada

    Cenário alternativo: módulo sem release anterior
      Dado um módulo sem nenhuma release tag ancestral
      Então target sai com code=true e infra=true e "last release: none"

    Cenário alternativo: build falha
      Dado um build / code / test vermelho
      Então build / image e build / release são pulados, nenhuma release tag existe e a build tag fica

    Cenário alternativo: build tag inválida
      Dado a tag build/foo.2026-11-21.001 com foo fora do modules.json, ou build/core-x
      Então target falha com a mensagem exata e nada é construído

    Cenário alternativo: builds sobrepostos do mesmo módulo
      Dado build/core.…001 rodando
      Quando build/core.…002 começa
      Então o build de …001 é cancelado, …002 publica core.…002, e um build de gateway segue em paralelo

    Cenário: deploy falho dispara rollback
      Dado core.…002 verde em staging e o verify de core.…003 falhando
      Quando o deploy de core.…003 termina
      Então o job rollback dispara deploy.yml na ref core.…003 com environment=staging e rollback_to=core.…002
      E o notify de …003 diz "failed" com "rolling back to core.…002"

    Cenário: rollback passa pelo mesmo track
      Dado o dispatch com rollback_to=core.…002 na ref core.…003
      Quando o deploy roda
      Então o run-name é "staging · rollback · core.…002 (from core.…003)"
      E preflight aceita …002 por estar gravada verde em staging, com requirements strict false
      E apply roda (forçado), deployment, migrate, rollout e verify fazem checkout de core.…002
      E record grava core.…002 com success e o notify diz "rolled back" com "core.…002 after core.…003 failed"

    Cenário alternativo: rollback que falha não encadeia
      Dado o verify do rollback falhando
      Então o job rollback é pulado e o notify diz "failed" com "rollback of core.…003 failed"

    Cenário alternativo: sem release anterior
      Dado o primeiro deploy de um módulo falhando no verify
      Então nada é disparado e o notify diz "no earlier release to roll back to"

    Cenário alternativo: release mais nova na fila
      Dado core.…004 com um run do deploy pendente em staging
      Quando o deploy de core.…003 falha
      Então nada é disparado e o notify diz "rollback skipped: core.…004 is queued"

    Cenário alternativo: apply falha
      Dado o apply de core.…003 falhando
      Então o job rollback é pulado

    Cenário alternativo: rollback_to inválido
      Dado um dispatch na ref core.…003 com rollback_to=gateway.…001 ou rollback_to=xyz
      Então release-start falha com "rollback_to <P> is not a release of core" (ou "invalid release tag")

    Cenário alternativo: rollback de produção
      Dado o deploy de produção de core.…003 falhando no verify com core.…002 verde em produção
      Então o rollback dispara com environment=production e passa pelo preflight de produção (restricted vault e record de staging de …002)

    Cenário: hook rollback aposentado
      Dado um módulo com infra/ci/deploy/rollback.sh
      Quando roda o conform
      Então ele reprova com "rollback.sh is retired in v2: a failed deploy dispatches a deploy of the previous release"
      E sem o arquivo e sem rollback= no deployment ele passa

    Cenário: render v2 sem dependência de módulos
      Dado dois modules.json com módulos diferentes e o mesmo vault
      Quando rodo render.py
      Então main.yml, build.yml e deploy.yml saem byte a byte iguais entre os dois, e todos referenciam @v2
      E o pr.yml continua com as trilhas por módulo

    Cenário: dir customizado chega ao deploy
      Dado modules.events.code.dir = modules/events/app
      Quando release-start roda para events.…001
      Então o deploy recebe code_dir=modules/events/app

    Cenário: plataforma
      Dado macOS e Linux
      Quando rodo tests/split, tests/target, tests/rollback, tests/releases, tests/render, tests/conform, tests/actions e tests/release
      Então a saída é idêntica nos dois

    Cenário: lunetamagica na v2 de ponta a ponta
      Dado o lunetamagica regenerado com --ref v2, sem rollback.sh
      Quando um PR é mergeado na main
      Então o split empurra build/core.…, o build publica core.… e o staging fica verde
      E a build tag não existe mais

    Cenário: drill de rollback no lunetamagica
      Dado core.A e core.B verdes em staging (B mais nova) e o ward com ROLLBACK_DRILL=core.A
      Quando disparo o deploy de staging na ref core.A
      Então o verify de A falha, o rollback para core.B roda e fica verde, e staging volta a B

# why

- **Rollback provado:** hoje cada projeto escreve um `rollback.sh` próprio do provedor, com `ROLLBACK_POINT`; ele quase nunca roda, não passa por `apply` nem `migrate` e não reverte a infra que a release falha aplicou. Como deploy da última release verde, o rollback usa os hooks que rodam em todo deploy, o `apply` reverte a infra e um hook some de todo projeto. Com o promote levando releases a produção sem humano, esse caminho precisa ser confiável.
- **Releases em ordem e completas:** o `main` não tem concurrency; dois merges seguidos podem publicar a 002 antes da 001 e o staging volta para a velha. E uma mudança cujo build falhou entra na release seguinte sem checagem, porque o próximo push só checa o próprio diff. Build por módulo com concurrency e detect desde a última release fecha os dois. O automerge do autofix vai aumentar o ritmo de merges, quando isso deixa de ser raro.
- **Workflows gerados iguais em todo projeto:** `main`, `build` e `deploy` passam a depender só do vault; adicionar um módulo mexe só no `modules.json` e no `pr.yml`; o `code.dir` customizado passa a chegar ao deploy. Fazer agora evita que promote e autofix escrevam duas vezes as mesmas partes (`render.py`, `deploy.yml`, tag publicada) e faz as duas nascerem na `v2`.
- Custo aceito: o caminho do merge ao staging fica uns 20–40 s mais lento (um workflow a mais e um conform a mais) e cada consumidor migra num PR.

# how

TDD em toda task de código: o tester escreve o teste vermelho a partir dos cenários, o builder implementa o mínimo e a suíte fica verde. Validação padrão do repo (`VALIDA`): `python3 -m py_compile actions/*/*.py tasks/check.py && python3 tasks/check.py && sh tasks/check_rendered.sh && for t in tests/*/run.sh; do sh "$t" || exit 1; done && shellcheck -S warning actions/*/*.sh examples/*/*/ci/**/*.sh tests/*/run.sh tasks/*.sh`.

**Feature flag:** sem Flipper. A ativação é a versão: só quem regenera com `--ref v2` muda; a `v1` fica congelada.

**Telas:** sem telas criadas ou editadas (pipelines de CI).

**`v1`/`v2`:** nenhum PR move a `v1`. A tag `v2` só é criada no PR 8, depois do merge dos PRs 1–7. Até lá, `main` do pipelines referencia `@v2` sem consumidor.
