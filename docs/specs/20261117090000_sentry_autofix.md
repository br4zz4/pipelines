# Autofix de Sentry issues com agente e PR

> **TLDR**: um workflow `autofix` gerado pelo render roda de hora em hora (ou por dispatch). Ele escolhe uma Sentry issue de produção, entrega o erro sem PII a um agente Claude isolado, que roda os mesmos hooks `ci/checks` do `code.yml` (e do `make <m>.test` do commons), e verifica de forma determinística que o teste de regressão falhava antes e passa depois. Só então abre um PR. Nos outros casos, deixa uma nota na Sentry issue.

# what

    Como dono do has_warranty (e de todo projeto br4zz4/pipelines), quero que erros novos de
    produção no Sentry virem PRs de correção já provados por um teste de regressão, para
    corrigir bugs reais sem precisar triar e reproduzir cada um à mão, sem abrir mão da
    revisão humana.

Glossário: `docs/CONTEXT.md` (**Sentry issue**, **Autofix**, Module, Hook, Release tag, Render, Conform, Default vault, Ward scope, Commons).

## Estado de partida (2026-11-18)

- A spec padrão (`20261115150000_standard_module_pipelines.md`) está implementada e a `v1` está publicada (`9c5864f`). Os reusables são `code.yml`, `infra.yml` e `deploy.yml`. Os hooks moram em `ci/checks/<step>.sh` e `ci/deploy/<step>.sh`. Todo checkout dos reusables usa `submodules: recursive`, e o `check.py` impõe isso.
- O `br4zz4/commons` está publicado (`v1`), e o has_warranty já o usa. `make <m>.test` roda o mesmo `ci/checks/test.sh` do CI, com o mesmo cwd e as mesmas variáveis. O hook é a implementação.
- `actions/step` carrega `<vault>:secrets.<m>.<side>.<env>` por default. No `code.yml`, o job `test` sobrescreve com `<vault>:secrets.ci.test`. O cache (`actions/cache`) salva no fim do job.
- `br4zz4/setup-ward@v1` sempre exporta `WARD_KEY_<NS>` para o `GITHUB_ENV` e não tem como desligar isso.
- No has_warranty, só o core reporta ao Sentry. `config.release` é o `K_REVISION` do Cloud Run (ex.: `has-warranty-staging-web-00094-8qb`), não a release tag, e `config.environment` é o `Rails.env`.

## Modelo

### Configuração (`.github/modules.json`)

```json
{
  "autofix": {
    "sentry_org": "brazza-tech",
    "sentry_project": "has_warranty",
    "sentry_url": "https://sentry.io",
    "schedule": "0 * * * *",
    "environments": ["production"],
    "min_events": 5,
    "max_per_day": 5,
    "reviewers": ["o_porpino"]
  }
}
```

| chave | obrigatória | default | regra |
|---|---|---|---|
| `sentry_org`, `sentry_project` | sim | — | string não vazia |
| `sentry_url` | não | `https://sentry.io` | `https://…` |
| `schedule` | não | `0 * * * *` | cron com 5 campos |
| `environments` | não | `["production"]` | lista não vazia de strings |
| `min_events` | não | `5` | inteiro ≥ 1 |
| `max_per_day` | não | `5` | inteiro ≥ 1 |
| `reviewers` | não | `[]` | lista de logins do GitHub |

Uma chave desconhecida dentro de `autofix` é erro de render. Sem a chave `autofix`, nada muda no projeto: o render produz os mesmos três arquivos, byte a byte.

### Workflow gerado no projeto (`.github/workflows/autofix.yml`)

O render passa a escrever um quarto arquivo quando a chave existe. O conform o trata como parte do padrão: se divergir do render, reprova. Se existir sem a chave, reprova como qualquer arquivo fora do padrão, a menos que esteja em `extra_workflows`.

```yaml
# generated by br4zz4/pipelines render — do not edit
name: autofix
on:
  schedule:
    - cron: '0 * * * *'
  workflow_dispatch:
    inputs:
      issue:
        description: Sentry issue short id; ignores the filter, the dedup and the daily cap
        required: true
        type: string
concurrency:
  group: autofix
  cancel-in-progress: false
permissions:
  contents: read
  actions: read
  pull-requests: read
jobs:
  conform:
    # mesmo job conform (mode: check) dos outros workflows gerados
  autofix:
    name: autofix
    needs: conform
    uses: br4zz4/pipelines/.github/workflows/autofix.yml@v1
    with:
      vault: has_warranty
      issue: ${{ inputs.issue || '' }}
      sentry_org: brazza-tech
      sentry_project: has_warranty
      sentry_url: https://sentry.io
      environments: production
      min_events: 5
      max_per_day: 5
      reviewers: o_porpino
      modules: '{"checkout":{"code":"modules/checkout/code","services":"postgres"},"core":{"code":"modules/core/code","services":"postgres"}}'
    secrets:
      WARD_KEY: ${{ secrets.WARD_KEY_HAS_WARRANTY }}
```

Nenhum job pede `id-token: write`. Sem token OIDC, nenhum código rodado pelo autofix consegue se autenticar num provedor por Workload Identity.

### Reusable `autofix.yml`: uma Sentry issue por execução

```
autofix / select ─► autofix / fix ─► autofix / verify ─► autofix / publish (sempre que select escolheu)
```

| job | runner | secrets que vê | o que faz |
|---|---|---|---|
| `select` | `blacksmith-2vcpu-ubuntu-2404` | `<ns>:secrets.ci.autofix` (`SENTRY_AUTH_TOKEN`), `GITHUB_TOKEN` (`actions: read`, `pull-requests: read`) | escolhe a Sentry issue, deduplica, aplica o teto diário, resolve o módulo, baixa o último evento, remove PII e publica o artifact `sentry` |
| `fix` | `blacksmith-4vcpu-ubuntu-2404` | `<ns>:secrets.ci.agent` (`CLAUDE_CODE_OAUTH_TOKEN`), `<ns>:secrets.ci.test`, `<ns>:secrets.<m>.code.test`, **sem exportar a chave ward** | toolchain, setup e serviços do módulo; roda o Claude Code; publica o artifact `autofix` (`result.json` + `fix.patch`) |
| `verify` | `blacksmith-4vcpu-ubuntu-2404` | os mesmos escopos que o `code.yml` usa em cada hook, **sem exportar a chave ward** | checkout limpo e hooks da base; aplica as regras de escopo, prova vermelho → verde e roda `lint` |
| `publish` | `blacksmith-2vcpu-ubuntu-2404` | `<ns>:secrets.ci.common` (`GH_PIPELINES_TOKEN`, `NOTIFY_WEBHOOK_URL`), `<ns>:secrets.ci.autofix` | push da branch e PR, ou só a nota; nota na Sentry issue; `notify` |

- Todo checkout usa `submodules: recursive`, porque um hook pode chamar `.commons/bin/commons`, e `persist-credentials: false`.
- `fix` e `verify` têm `permissions: contents: read` e nada mais.
- `fix` e `verify` só **restauram** o cache (`actions/cache/restore`) e nunca salvam. Os testes que o agente escreve rodam nesses jobs, e um cache salvo ali seria restaurado pelos builds do `main`.

### Paridade de hooks

O autofix roda os hooks como o `code.yml` roda, e o `code.yml` roda como o commons roda localmente:

| hook | `code.yml` | autofix (`fix` via `ci-hook`, `verify` via `step`) | local |
|---|---|---|---|
| `test` | `step` com `scopes: <ns>:secrets.ci.test` + serviços | igual | `make <m>.test` |
| `lint` | `step` com o escopo default `<ns>:secrets.<m>.code.test` | igual | `make <m>.lint` |

O agente **não** usa `make`. Com `COMMONS_VAULT` preenchido, o commons chama `ward exec` e precisa da chave do vault, que o agente nunca tem. Os valores do escopo já estão no ambiente do job, e o `ci-hook` roda o mesmo `actions/hook/hook.sh` que a action `step` roda.

### Seleção (`select`)

- **Cron:** consulta `GET {sentry_url}/api/0/projects/{org}/{project}/issues/` com `query=is:unresolved level:[error,fatal] firstSeen:-24h times_seen:>={min_events}`, um parâmetro `environment` por item de `environments`, `statsPeriod=24h` e `sort=freq`. Percorre os resultados em ordem e escolhe a primeira Sentry issue que não está deduplicada.
- **Dedup:** uma Sentry issue é pulada se existe um PR em qualquer estado com head `fix/sentry-<short-id em minúsculas>` (`gh api repos/{repo}/pulls?state=all&head={owner}:{branch}`), ou se alguma nota dela começa com `[autofix]` (endpoint de comentários da issue na API do Sentry, confirmado na doc durante o PR 2).
- **Teto diário:** antes de consultar o Sentry, conta as execuções de `autofix.yml` criadas nas últimas 24h cujo job `autofix / fix` não terminou `skipped`. Se o total for `>= max_per_day`, escreve `daily cap reached (<n>/<max>)` no summary e encerra sem escolher nada.
- **Dispatch manual** (`issue` preenchido): ignora o filtro, o dedup e o teto. Falha com `::error::<id> does not belong to <org>/<project>` se a Sentry issue for de outro projeto.
- **Módulo:** `release` do último evento, com `${release%%.*}`. A release precisa ser uma release tag (`core.2026-11-17.001`). Se o prefixo não for um módulo de `modules`, o `select` emite `outcome=rejected` e `reason=release '<release>' names no module`. Nesse caso `fix` e `verify` são pulados e o `publish` só deixa a nota.
- **Sem candidata:** escreve `nothing to fix` no summary. Os demais jobs são pulados e não há notify.
- **Saídas:** `issue` (short id), `issue_id`, `title`, `url`, `module`, `code_dir`, `services`, `outcome` (`selected`|`rejected`) e `reason`.

### Remoção de PII (allow-list)

O `issue.json` entregue ao agente contém **só**:

- da issue: `shortId`, `title`, `culprit`, `level`, `platform`, `count`, `firstSeen`, `lastSeen`;
- do evento: `release`, `environment`, `tags` com as chaves `transaction`, `handled`, `mechanism`, `level`, `runtime`, `runtime.name`;
- das exceptions: `type`, `value`, `mechanism.type` e, por frame: `filename`, `module`, `function`, `lineno`, `colno`, `in_app`, `context_line`, `pre_context`, `post_context`. Os `vars` dos frames ficam de fora;
- dos breadcrumbs (os 30 últimos): `timestamp`, `category`, `level` e `message`, sem `data`.

Em toda string mantida, e-mails viram `<email>`, IPv4/IPv6 viram `<ip>` e sequências com aparência de token (`[A-Za-z0-9_\-]{32,}`) viram `<token>`. `value` é truncado em 2000 caracteres e `message` em 500.

### Agente (`fix`)

- Claude Code CLI numa versão exata, fixada no `action.yml` (a estável mais recente no momento da implementação), instalada com `npm install -g @anthropic-ai/claude-code@<versão>` sobre `actions/setup-node@v4` (`node-version: 22`).
- **Guard antes de tudo:** o job sai com 1 (`::error::agent environment leaks <nome>`) se existir no ambiente `GH_PIPELINES_TOKEN`, `SENTRY_AUTH_TOKEN`, `GITHUB_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_URL` ou qualquer `WARD_KEY_*`. Também sai com 1 se `git remote get-url origin` ou `git config --get-regexp 'http\..*\.extraheader'` mostrar credencial.
- Execução: `claude -p "$(cat prompt)" --model opus --max-turns 40 --output-format json --allowedTools "Read,Edit,Write,Glob,Grep,Bash(ci-hook:*)" --disallowedTools "WebFetch,WebSearch,Task"`. O job tem `timeout-minutes: 30`.
- `ci-hook <lint|test> [args…]` é um script da action instalado no `PATH`:
  1. restaura `<code_dir>/ci` a partir da **cópia da base** feita antes de o agente começar (`$RUNNER_TEMP/base-ci`). Uma edição do agente em `ci/` nunca é executada;
  2. roda `actions/hook/hook.sh` com `STEP=<step>`, cwd em `<code_dir>`, `MODULE`, `ENVIRONMENT=test` e os argumentos, via `env -u CLAUDE_CODE_OAUTH_TOKEN -u ANTHROPIC_API_KEY`;
  3. qualquer outro step sai com 2.
- O `hook.sh` passa a repassar `"$@"` ao script. A action `hook` não passa argumentos, então o CI não muda. Assim `ci-hook test <arquivo>` equivale a `make <m>.test ARGS=<arquivo>`.
- O prompt (`actions/agent/prompt.md`) é neutro de linguagem e manda:
  - ler `.autofix/issue.json`;
  - mexer só em `<code_dir>`, fora de `ci/` e de `mise.toml`;
  - escrever primeiro um teste de regressão que reproduz o erro e confirmar o vermelho com `ci-hook test`;
  - corrigir o mínimo e confirmar o verde com `ci-hook test` e `ci-hook lint`;
  - terminar escrevendo `.autofix/result.json`:

```json
{ "status": "fixed", "tests": ["modules/core/code/test/models/billing_test.rb"], "summary": "causa raiz e correção em até 1000 caracteres" }
```

  `status` é `fixed` ou `gave_up`. No `gave_up`, o `summary` explica o diagnóstico e o motivo.
- Depois do agente, a action gera `.autofix/fix.patch` com `git add -N . && git diff --binary --ignore-submodules=all -- . ':!.autofix'` e publica `result.json` + `fix.patch` no artifact `autofix` (retenção de 7 dias).
- Saídas do job: `status` (`fixed`|`gave_up`|`failed`) e `summary`. `failed` cobre `result.json` ausente ou inválido, CLI com saída diferente de 0 e timeout. Neste último caso o job falha e o `publish` lê `needs.fix.result`.
- Risco residual aceito: os testes que o agente escreve executam código no `fix` e no `verify`, inclusive com acesso à rede. Por isso esses jobs só veem valores de **teste**, sem chave ward, sem tokens de GitHub ou Sentry, sem OIDC e sem salvar cache. O banco vem dos `services` do módulo. Os valores de `secrets.ci.test` e `secrets.<m>.code.test` são próprios de teste e nunca reaproveitam staging.

### Verificação (`verify`)

Roda só se `fix.status == fixed`, nesta ordem e parando na primeira reprovação. Cada reprovação vira `reason`:

1. `scope`:
   - o patch não pode estar vazio (`empty patch`);
   - nenhum arquivo pode casar `.github/**`, `.ward/**`, `.commons/**`, `.gitmodules`, `commons.ctx`, `**/ci/**` ou `**/mise.toml` (`forbidden path <arquivo>`);
   - todo arquivo precisa estar dentro de `<code_dir>/` (`outside module <arquivo>`);
   - `tests` não pode ser vazio, e todo item de `tests` precisa estar no patch (`test <arquivo> not in patch`).
2. `red`: aplica só os arquivos de `tests` (`git apply --include=<arquivo>` por item) e roda o hook `test` pela action `step` (`continue-on-error: true`). Se ele **passar**: `regression test passed before the fix`.
3. `green`: `git checkout -- . && git clean -fd`, aplica o patch inteiro e roda `test` (`test failed with the fix`) e `lint` (`lint failed with the fix`).

Os hooks rodam pela action `step` com `export-key: false`, `cache: restore`, os escopos da tabela "Paridade de hooks", os serviços do módulo e os hooks da base, porque o scope reprovou qualquer patch em `ci/`.

### Publicação (`publish`)

`if: always() && needs.select.outputs.issue != ''`. O desfecho sai de `select`, `fix` e `verify`:

| desfecho | condição | ações |
|---|---|---|
| `opened` | `verify` success | commit `fix: <short-id> <title>` (truncado em 60 caracteres) com autor `github-actions[bot]`; push de `fix/sentry-<short-id>` com `GH_PIPELINES_TOKEN`; `gh pr create --base <github.ref_name> --label autofix` (cria a label se faltar) com os `reviewers`; nota `[autofix] opened <pr url>` |
| `gave up` | `fix.status == gave_up` | nota `[autofix] gave up: <summary>` |
| `rejected` | `select.outcome == rejected` ou `verify` failure | nota `[autofix] rejected: <reason> (<run url>)` |
| `failed` | `fix` failure/cancelled ou erro no próprio `publish` | nota `[autofix] failed (<run url>)` |

O corpo do PR traz:
- `Fixes <SHORT-ID>` com o link;
- o `summary` do agente;
- os testes de regressão;
- o link do run do `verify`;
- a linha `Gerado pelo autofix. Revise antes do merge; nada é mergeado automaticamente.`

Como o PR é aberto com o PAT, o `pull_request` do projeto dispara e o `check/pr` roda.

O último step, `notify` (`if: always()`), chama a action `notify` com:
- `kind: autofix`, `module: <módulo>` e `tag: <short-id>`;
- `url`: a do PR ou, se não houver PR, a da Sentry issue;
- `status`: igual ao desfecho.

A mensagem é `<emoji> autofix <short-id> (<módulo>): <status>. <url> <run url>`.

## out of scope

- Relay em tempo real (alerta do Sentry → Worker → `repository_dispatch`): fica para a próxima spec.
- Auto-merge, deploy, ou qualquer mudança de status da Sentry issue feita pelo pipeline (ela resolve pela integração GitHub do Sentry quando o commit chega numa release).
- Nova tentativa automática: uma tentativa por Sentry issue. O dispatch manual é o caminho para tentar de novo.
- Caminhos proibidos configuráveis por projeto.
- Correções que atravessam módulos ou mexem no lado `infra`: viram `rejected`.
- Sentry no checkout do has_warranty: o módulo não reporta ao Sentry hoje, então nenhuma Sentry issue aponta para ele.
- Bloquear a rede de saída nos jobs `fix` e `verify`.
- Seer/Autofix nativo do Sentry.
- Mais de uma Sentry issue por execução (sem `matrix`, regra da spec padrão).
- `ANTHROPIC_API_KEY`: só `CLAUDE_CODE_OAUTH_TOKEN`. Trocar depois é só mudar o valor no ward e a variável na action.
- Windows.

## acceptance criteria

    Cenário: cron escolhe a Sentry issue mais frequente elegível
      Dado três Sentry issues de produção não resolvidas, vistas pela primeira vez nas últimas 24h, com 3, 7 e 12 eventos
      E min_events 5
      Quando o autofix roda pelo cron
      Então o select escolhe a de 12 eventos e emite o módulo da release dela

    Cenário alternativo: nada elegível
      Dado nenhuma Sentry issue que passe no filtro
      Quando o autofix roda pelo cron
      Então o summary mostra "nothing to fix", fix, verify e publish aparecem pulados e não há notify

    Cenário alternativo: dedup
      Dado que a Sentry issue mais frequente já tem PR fix/sentry-<id> fechado, ou uma nota "[autofix] …"
      Quando o autofix roda pelo cron
      Então ela é pulada e a próxima elegível é escolhida

    Cenário alternativo: teto diário
      Dado 5 execuções nas últimas 24h em que autofix / fix não foi pulado, e max_per_day 5
      Quando o autofix roda pelo cron
      Então o summary mostra "daily cap reached (5/5)" e o Sentry não é consultado

    Cenário: dispatch manual força nova tentativa
      Dado uma Sentry issue com nota "[autofix] gave up" e o teto diário atingido
      Quando disparo o autofix com issue=<id>
      Então o select a escolhe mesmo assim

    Cenário alternativo: dispatch de Sentry issue de outro projeto
      Quando disparo o autofix com o id de uma Sentry issue de outro projeto
      Então o select falha com "does not belong to <org>/<project>"

    Cenário alternativo: release sem módulo
      Dado o último evento com release "has-warranty-staging-web-00094-8qb"
      Quando o select roda
      Então fix e verify são pulados
      E a Sentry issue recebe "[autofix] rejected: release 'has-warranty-staging-web-00094-8qb' names no module"

    Cenário: PII não chega ao agente
      Dado um evento com user, ip, cookies, headers, request.data, vars nos frames e um e-mail no value da exception
      Quando o select gera o issue.json
      Então nenhum desses campos existe e o e-mail aparece como "<email>"

    Cenário: agente isolado
      Dado o job autofix / fix
      Então o ambiente não tem GH_PIPELINES_TOKEN, SENTRY_AUTH_TOKEN, GITHUB_TOKEN, ACTIONS_ID_TOKEN_REQUEST_URL, WARD_KEY_* nem credenciais no remote do git
      E um hook rodado por ci-hook não enxerga CLAUDE_CODE_OAUTH_TOKEN
      E editar <code_dir>/ci/checks/test.sh no workspace não muda o que ci-hook test executa

    Cenário alternativo: ambiente vazando
      Dado o job autofix / fix com WARD_KEY_HAS_WARRANTY no ambiente
      Então o guard falha com "agent environment leaks WARD_KEY_HAS_WARRANTY" antes de o Claude rodar

    Cenário: paridade com o code.yml e o commons
      Dado o módulo core
      Quando o agente roda ci-hook test test/models/billing_test.rb
      Então roda o mesmo modules/core/code/ci/checks/test.sh que core / code / test e make core.test rodam
      E o script recebe o arquivo como argumento, MODULE=core, ENVIRONMENT=test e os valores de secrets.ci.test

    Cenário: autofix não envenena o cache
      Dado os jobs autofix / fix e autofix / verify
      Então nenhum deles salva cache, só restaura

    Cenário: correção provada abre PR
      Dado um bug reproduzível no módulo core
      Quando o agente entrega status fixed, com um teste que falha sem a correção e passa com ela
      Então verify passa em scope, red e green
      E existe o PR fix/sentry-<id> com a label autofix, os reviewers e "Fixes <ID>" no corpo
      E o check/pr roda nesse PR
      E a Sentry issue recebe "[autofix] opened <pr url>" e o notify envia "opened"

    Cenário alternativo: agente desiste
      Quando o agente entrega status gave_up
      Então nenhuma branch é criada, a Sentry issue recebe "[autofix] gave up: <summary>" e o notify envia "gave up"

    Cenário alternativo: caminho proibido
      Dado um patch que altera modules/core/code/ci/checks/test.sh, .github/workflows/pr.yml, .commons ou commons.ctx
      Então verify reprova com "forbidden path <arquivo>", não há PR e o notify envia "rejected"

    Cenário alternativo: patch fora do módulo
      Dado o módulo core e um patch que altera modules/checkout/code/…
      Então verify reprova com "outside module <arquivo>"

    Cenário alternativo: teste que não reproduz
      Dado um teste de regressão que passa sem a correção
      Então verify reprova com "regression test passed before the fix"

    Cenário alternativo: correção que quebra a suíte ou o lint
      Dado um patch em que test ou lint falha com a correção aplicada
      Então verify reprova com "test failed with the fix" ou "lint failed with the fix"

    Cenário alternativo: agente falha
      Dado o agente estourando os 30 minutos, saindo com erro ou sem result.json válido
      Então a Sentry issue recebe "[autofix] failed (<run url>)" e o notify envia "failed"

    Cenário alternativo: execuções sobrepostas
      Dado um autofix em andamento
      Quando outro é disparado
      Então o segundo espera o primeiro terminar (concurrency autofix, sem cancelar)

    Cenário: setup-ward sem exportar a chave
      Dado setup-ward com export-key false e um escopo com FOO=1
      Quando o step seguinte roda
      Então FOO está no ambiente e nenhum WARD_KEY_* está
      E com export-key omitido o comportamento é o de hoje

    Cenário: render com autofix
      Dado um modules.json com a chave autofix
      Quando rodo render.py
      Então ele escreve autofix.yml com o cron, os inputs e o JSON de módulos da configuração, e os defaults aplicados

    Cenário alternativo: render sem autofix ou com configuração inválida
      Dado um modules.json sem a chave autofix
      Então render.py não escreve autofix.yml e os três workflows ficam byte a byte iguais
      E com sentry_org ausente, min_events 0, schedule com 4 campos ou chave desconhecida, render.py falha citando a chave

    Cenário alternativo: autofix.yml editado à mão
      Dado um autofix.yml diferente do render
      Quando roda o conform
      Então ele reprova citando autofix.yml

    Cenário: Sentry recebe a release tag
      Dado o core do has_warranty buildado com a tag core.2026-11-18.001
      Quando um erro acontece em staging e depois, com a mesma imagem promovida, em produção
      Então o evento do Sentry traz release "core.2026-11-18.001" nos dois ambientes

    Cenário: plataforma
      Dado macOS e Linux
      Quando rodo tests/sentry, tests/agent, tests/patch e tests/render
      Então a saída é idêntica nos dois

    Cenário: has_warranty ativado
      Dado o has_warranty com autofix configurado e as releases reportadas como release tags
      Quando disparo o autofix com uma Sentry issue real
      Então o run termina num dos quatro desfechos, com a nota correspondente na Sentry issue

# why

Hoje um erro de produção no Sentry só vira correção quando alguém o vê, reproduz, escreve o teste e corrige. No has_warranty já existem Sentry issues abertas há dias, como `HAS_WARRANTY-A` com 81 eventos e `HAS_WARRANTY-5` com 29, e nenhum fluxo as transforma em trabalho.

Um agente consegue fazer a parte mecânica: ler o stack trace, reproduzir em teste e propor a correção. Mas, sem prova e sem isolamento, ele gera PRs que "parecem corrigidos" e abre uma porta para prompt injection vinda de texto controlado pelo usuário no evento.

Esta spec só deixa o PR chegar ao humano depois que o pipeline verificou o vermelho → verde de forma determinística, com os mesmos hooks que o CI e o commons já usam. O agente não tem acesso a nenhum segredo além dos valores de teste e do próprio token. Como tudo é gerado pelo render, qualquer projeto br4zz4 ganha o autofix com uma chave no `modules.json`.

# how

TDD em toda task de código: o tester escreve o teste vermelho a partir dos cenários, o builder implementa o mínimo e a suíte fica verde. Validação padrão do pipelines: `python3 tasks/check.py && sh tasks/check_rendered.sh && for t in tests/*/run.sh; do sh "$t" || exit 1; done && shellcheck -S warning actions/*/*.sh examples/*/*/ci/**/*.sh tests/*/run.sh tasks/*.sh`. Sem telas.

**Pré-requisito externo:** a integração GitHub do Sentry instalada na org `brazza-tech` com acesso ao repo do has_warranty. Ela é verificada no PR 9.

**Tag `v1`:**
- Os PRs 2–7 entram no `main` do pipelines sem mover a `v1`.
- Se outra entrega mover a `v1` no meio da sequência, nada quebra: o reusable e as actions novas não têm caller até o render (PR 6), e um projeto sem a chave `autofix` renderiza igual.
- O PR 9 publica com `sh tasks/release.sh v1 --push`.
