# Sentry release e deploy a cada Build e Deploy

> **TLDR**: com a chave `sentry` no `.github/modules.json`, o Build cria a Sentry release `<projeto>@<release tag>` com os commits desde a anterior, o hook de imagem recebe `SENTRY_RELEASE` com esse nome para o app reportar no SDK, e todo Deploy que grava verde (inclusive Rollback) marca o deploy da release no ambiente. Falha no Sentry nunca reprova Build nem Deploy. Sem a chave, nada muda.

Glossário: `docs/CONTEXT.md` (**Sentry release**, Release, Release tag, Build, Deploy, Rollback, Record, Render, Conform). A configuração `sentry` é a mesma que o autofix usa (`docs/specs/20261121100100_autofix_critical_issues.md`, ajustada nesta spec).

# what

    Como dono de um projeto br4zz4/pipelines, quero que o Sentry saiba de cada release nova e
    de quando ela entrou em staging e em produção, para ver em que release um erro começou,
    qual commit é o suspeito e se o deploy de agora piorou as coisas, sem passo manual.

## out of scope

- Upload de source maps ou debug files.
- Criar o projeto, a Internal Integration/token ou instalar a integração GitHub no Sentry (passos manuais do dono, descritos no how).
- Adoção nos projetos: o has_warranty adota em PR próprio do dono (issue aberta no repo); o lunetamagica adota quando tiver projeto no Sentry (`brazza-tech/lunetamagica` `docs/specs/20261120210600_lucid_backoffice_sentry.md`).
- Mudar o webhook do `notify` (o aviso no Slack continua como está).
- Self-hosted Sentry além de aceitar `url` configurável.
- Reprovar ou atrasar um deploy por causa do Sentry.

## Modelo

### Configuração (`.github/modules.json`)

```json
{
  "sentry": {
    "org": "brazza-tech",
    "project": "has_warranty",
    "url": "https://sentry.io"
  }
}
```

| chave | obrigatória | default | regra |
|---|---|---|---|
| `sentry` | não | ausente | objeto; ausente = nada muda |
| `sentry.org`, `sentry.project` | sim (com `sentry`) | — | string não vazia, `[a-z0-9][a-z0-9_-]*` |
| `sentry.url` | não | `https://sentry.io` | `https://…`, sem barra final |

Chave desconhecida em `sentry` é erro de render. Todos os módulos do projeto vão para o mesmo projeto do Sentry (o módulo já está no nome pela release tag).

### Nome

`SENTRY_RELEASE = <sentry.project>@<release tag>`, ex.: `has_warranty@core.2026-11-21.001`.

### Credencial

`SENTRY_AUTH_TOKEN` em `<ns>:secrets.ci.common`, token de Internal Integration (ou de organização) com `project:releases` (criar release, associar commits, criar deploy) e `org:read`. Ausente com a chave `sentry` presente → `::warning` e nada é enviado; o Build/Deploy segue.

### Chamadas (HTTP, `curl`, sem `sentry-cli`)

1. **release** (job `release` do Build, depois do `stamp`):
   - `POST {url}/api/0/organizations/{org}/releases/` com `{"version": SENTRY_RELEASE, "projects": [project], "refs": [{"repository": "<owner>/<repo>", "commit": "<sha da release tag>"}]}`. Sem `previousCommit`: o Sentry usa o commit da release anterior do projeto.
   - Se a resposta for 4xx citando repositório/integração, repete sem `refs` e emite `::warning::sentry: release created without commits (no GitHub integration for <owner>/<repo>)`.
   - 409/208 (já existe) conta como sucesso (re-run do Build).
   - `PUT {url}/api/0/organizations/{org}/releases/{version}/` com `{"dateReleased": "<agora UTC ISO8601>"}` (finaliza).
2. **deploy** (job `record` do Deploy, só com `state` `success`):
   - `POST {url}/api/0/organizations/{org}/releases/{version}/deploys/` com `{"environment": "<staging|production>", "name": "<release tag>", "url": "<url do verify, se houver>", "dateFinished": "<agora>"}`.
   - Release inexistente (404, ex.: Build antigo antes da chave) → cria a release como no passo 1 e repete o deploy uma vez.
   - Um Rollback que grava verde marca o deploy da release para a qual voltou; um Deploy que falha não marca nada.
3. Toda chamada: `curl -fsS --max-time 15 --retry 2`; qualquer falha restante vira `::warning::sentry: …` com o status HTTP e a etapa; o script sai 0. O token nunca aparece no log (`::add-mask::` antes do uso).
4. O resultado vai para o summary do run: `Sentry release <version>: created|exists|failed` e `deploy <env>: marked|failed`, com link `{url}/organizations/{org}/releases/{version}/`.

### Ponte para o app

O hook `image` (`ci/checks/build.sh` do projeto) passa a receber `SENTRY_RELEASE` no ambiente, como já recebe `TAG`. É o projeto quem repassa para a imagem (`--build-arg SENTRY_RELEASE="$SENTRY_RELEASE"`) e o app que o usa no `Sentry.init` (`release`). Sem a chave `sentry`, a variável vem vazia.

## acceptance criteria

    Cenário: Build cria a Sentry release com commits
      Dado um projeto com "sentry": {"org": "brazza-tech", "project": "has_warranty"} e SENTRY_AUTH_TOKEN no ward
      Quando o Build de core.2026-11-21.001 publica a release tag
      Então o Sentry recebe POST de release com version "has_warranty@core.2026-11-21.001", projects ["has_warranty"] e refs com o repositório e o sha da tag
      E depois o PUT com dateReleased
      E o summary mostra "Sentry release has_warranty@core.2026-11-21.001: created" com o link

    Cenário: hook de imagem recebe o nome
      Dado o mesmo projeto
      Quando o job image roda o hook build
      Então o hook vê SENTRY_RELEASE=has_warranty@core.2026-11-21.001 e TAG=core.2026-11-21.001

    Cenário alternativo: sem integração GitHub no Sentry
      Dado que o POST com refs responde 400 citando o repositório
      Então o script repete sem refs, a release é criada e há ::warning de release sem commits

    Cenário alternativo: re-run do Build
      Dado a release já existente no Sentry
      Quando o job release roda de novo
      Então o POST responde "já existe", o script segue para o PUT e o summary mostra "exists"

    Cenário: Deploy verde marca o deploy
      Dado a release has_warranty@core.2026-11-21.001 no Sentry
      Quando o Deploy de staging grava success no record
      Então o Sentry recebe POST de deploy com environment "staging", name "core.2026-11-21.001" e a url do verify
      E o mesmo vale para production

    Cenário: Deploy falho não marca
      Quando o verify falha e o record grava failure
      Então nenhuma chamada de deploy é feita ao Sentry

    Cenário: Rollback marca a release para a qual voltou
      Dado um Deploy de core.2026-11-21.002 que falhou e disparou o Rollback para core.2026-11-21.001
      Quando o Rollback grava success
      Então o Sentry recebe o deploy de has_warranty@core.2026-11-21.001 no ambiente

    Cenário alternativo: release inexistente no deploy
      Dado uma release tag construída antes da chave sentry existir
      Quando o Deploy grava success
      Então o deploy responde 404, o script cria a release e repete o deploy uma vez

    Cenário alternativo: Sentry fora do ar ou lento
      Dado o Sentry respondendo 5xx ou excedendo 15 s depois dos retries
      Então o job emite ::warning com a etapa e o status, sai 0, e o Build publica a release tag / o Deploy segue para notify

    Cenário alternativo: token ausente
      Dado a chave sentry sem SENTRY_AUTH_TOKEN no ward
      Então há ::warning "sentry: SENTRY_AUTH_TOKEN missing in <ns>:secrets.ci.common" e nenhuma chamada

    Cenário: projeto sem a chave
      Dado .github/modules.json sem "sentry"
      Então o render gera os mesmos workflows de antes (byte a byte), o job release e o record não chamam o Sentry e SENTRY_RELEASE chega vazio ao hook

    Cenário alternativo: configuração inválida
      Quando "sentry" não tem org, tem project vazio, url sem https, ou uma chave desconhecida
      Então render.py falha citando a chave e o conform reprova

    Cenário: token não vaza
      Então o valor de SENTRY_AUTH_TOKEN nunca aparece no log do job (mascarado) nem no summary

# why

Hoje o Sentry do has_warranty não sabe de nenhuma release: o SDK manda `RELEASE_TAG` (sem projeto, colidiria com o lunetamagica, que também tem o módulo `core`), mas não há release criada com commits nem marca de deploy, então não há "erro novo nesta release", commit suspeito nem comparação antes/depois do deploy. A pipeline é o único lugar que sabe, para todo projeto, quando uma release nasce e quando entra em cada ambiente; fazer isso em cada app seria repetir e esquecer.

# how

Regras do repo: scripts POSIX `sh` (shellcheck `-S warning`), render em Python, testes em `tests/<nome>/run.sh` com Triple-A e `curl` falso (padrão de `tests/actions/run.sh`), sem comentários explicativos além do cabeçalho de uma linha que os scripts já usam, workflows passando pelo `tasks/check.py`.

**Feature flag:** a chave `sentry` é a flag por projeto: sem ela, render idêntico ao atual (cenário "projeto sem a chave"). Não há código temporário a remover.

**Telas:** sem telas.

**Staging:** `staging: none` (repo de pipeline; a prova em staging é o primeiro Build/Deploy do has_warranty com a chave, fora desta spec).

**Passos manuais do dono (antes de um projeto ligar a chave):** criar no Sentry uma Internal Integration com `project:releases` e `org:read`; gravar o token em `<ns>:secrets.ci.common.SENTRY_AUTH_TOKEN`; instalar a integração GitHub da org no Sentry com acesso ao repositório (opcional: sem ela a release sai sem commits, com warning).
