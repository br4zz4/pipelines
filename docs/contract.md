# Contract

What a repository must provide for `br4zz4/pipelines@v2` to run it, and what the
pipelines guarantee in return. Everything is convention plus one file:
`.github/modules.json`.

## Files of a project

```
.github/modules.json                  the registry — the only file edited by hand
.github/actions/setup/action.yml      authentication and system packages; never a language
.github/workflows/{pr,main,build,deploy}.yml   GENERATED by conform
.ward/config.yaml                     vaults <ns> (or <ns>::default) and <ns>::restricted
.ward/vaults/**                       encrypted, committed
modules/<m>/code/mise.toml            toolchain of the code side
modules/<m>/code/run/{lint,audit,test}       preferred; same script runs locally in the container and in CI
modules/<m>/code/ci/checks/{lint,audit,test}.sh   still accepted when run/<step> is absent
modules/<m>/code/ci/checks/build.sh
modules/<m>/infra/mise.toml           toolchain of the infra side
modules/<m>/infra/ci/checks/{validate,plan}.sh
modules/<m>/infra/ci/deploy/{apply,deployment,migrate,rollout,verify}.sh
```

## Registry — `.github/modules.json`

```json
{
  "shared": [".github/", ".ward/", "Makefile"],
  "extra_workflows": ["cleanup.yml"],
  "modules": {
    "core":    { "services": ["postgres"] },
    "gateway": {},
    "events":  { "services": ["postgres", "redis"], "code": { "dir": "modules/events/app" } }
  }
}
```

| key | meaning |
|---|---|
| `shared` | paths that count as a change for every module |
| `extra_workflows` | files allowed next to `pr`, `main`, `build` and `deploy` in `.github/workflows/`; default `[]` |
| `modules.<m>.services` | subset of `postgres` and `redis`; only `<module> / code / test` starts them (`build / code / test` too; `deploy / verify` runs without services) |
| `modules.<m>.code.dir`, `modules.<m>.infra.dir` | default `modules/<m>/code` and `modules/<m>/infra` |
| `promote` | object; its presence turns on the generated `promote.yml` (see Promote); absent changes nothing |
| `promote.max_per_day` | integer ≥ 1, promotions allowed per 24 hours; absent means no limit. An unknown key is a render error |
| `sentry` | object; its presence turns on the Sentry release and deploy marks (see Sentry releases); absent changes nothing |
| `sentry.org`, `sentry.project` | required with `sentry`; slug `[a-z0-9][a-z0-9_-]*`. Every module of the project reports to the same Sentry project |
| `sentry.url` | optional, default `https://sentry.io`; `https://…` without a trailing slash. An unknown key in `sentry` is a render error |
| `autofix` | object; its presence turns on the generated `autofix.yml` (see Autofix); absent changes nothing |
| `autofix.max_per_day` | integer ≥ 0, autofix runs allowed per 24 hours; absent or `0` means no limit |
| `autofix.sentry` | object; its presence turns on the generated `sentry-intake.yml`; requires the top-level `sentry` key, which supplies `org`, `project` and `url` |
| `autofix.sentry.schedule` | cron with 5 fields; default `0 * * * *` |
| `autofix.sentry.environments` | non-empty list of Sentry environments; default `["production", "staging"]` |
| `autofix.sentry.min_events` | integer ≥ 1, events in the last 24 hours; default `5`. An unknown key in `autofix` or `autofix.sentry` (`org`, `project` and `url` included) is a render error |

A module name matches `[a-z][a-z0-9_]*`: it is the tag prefix and a job id. The
project namespace `<ns>` is read from `.ward/config.yaml`; the GitHub secrets are
`WARD_KEY_<NS>` and `WARD_KEY_<NS>_RESTRICTED` with `<NS>` upper-cased the way
ward derives it (`has_warranty` → `WARD_KEY_HAS_WARRANTY`).

## Hooks — a closed vocabulary

| side | hook | job (GitHub UI) | ward environment |
|---|---|---|---|
| code | `lint`, `audit`, `test` | `<module> / code / lint`, `… / audit`, `… / test` | `test` |
| code | `regression` | `promote / regression` (promote only) | `test` |
| code | `e2e` | `promote / e2e` (promote only) | `staging` |
| code | `build` | `<module> / code / build` (main only) | `staging` |
| infra | `validate` | `<module> / infra / validate` | `test` |
| infra | `plan` | `<module> / infra / plan` | `staging` |
| infra | `apply`, `deployment`, `verify` | `deploy / apply`, `… / deployment`, `… / verify` | `staging` or `production` |
| infra | `migrate`, `rollout` (optional) | `deploy / migrate`, `… / rollout` | `staging` or `production` |

- **Every hook is mandatory, except `migrate` and `rollout`.** Those two are optional: without the script the job prints `skipping` and passes, so a project whose `deployment` does everything keeps working.
- **Every other hook is mandatory.** A missing script fails the step
  (`::error::missing ci/checks/<hook>.sh`, or `missing run/<hook> or ci/checks/<hook>.sh` for lint/audit/test, or `ci/deploy/<hook>.sh`). A module with nothing to do keeps a script
  that prints why and exits 0.
- A `ci/<context>/*.sh` outside the table is rejected by conform. Helpers live next to the
  hooks (for example `lib/`), never in `ci/`.
- A hook runs with its side directory as the working directory and receives
  `MODULE`, `ENVIRONMENT`, `TAG`, `PREVIOUS_TAG` (deploy hooks: the last release recorded green in the environment, empty when there is none) and `CI_CACHE_DIR` (`<dir>/.ci-cache`, restored
  by the cache step) plus the values of its ward scope.
- `chmod +x` is neither required nor trusted: a non-executable script runs with `sh`.
- `regression` and `e2e` are mandatory only when the registry has the `promote` key. `regression` runs on a runner
  with the module's `services`; `e2e` receives `TARGET_URL` (the Release URL) and its tests live in `<code_dir>/e2e/`.
  Either may write `<code_dir>/tmp/artifacts/failures.md` (test names, assertion, stack; no secret): it goes,
  masked and truncated to 20 000 characters, into the Critical issue. `tmp/artifacts/` exists only on the runner.
- The `test` hook of a pull request receives `BASE_SHA`, the merge-base with the base branch; it is empty on `main`
  and on dispatch, and an empty value means run everything. What counts as impacted is the project's decision.
- `verify` writes `url=<url>` to `$GITHUB_OUTPUT`; with `promote` on it also writes `release_url=<url>`, the address
  that serves that release (required in staging; a provider without one writes its default environment URL). There is no `rollback` hook and no rollback
  point (retired in v2): a failed deploy dispatches a deploy of the previous release.
  conform rejects a leftover `ci/deploy/rollback.sh`.
- The hook is the implementation. `make <module>.<step>` from `br4zz4/commons` runs the
  same script locally, with the same working directory and variables.

## Workflows

Each side of each module is a literal job of the project workflow that calls a reusable
workflow (`code.yml`, `infra.yml`, `deploy.yml`); the jobs of the reusable have literal names,
so the graph reads `<module> / <side> / <job>`. No `name:` holds an expression, every step is named, only the jobs of the `deploy.yml` reusable use `environment:` (and only as `${{ inputs.environment == 'production' && 'production' || 'staging' }}`) and no job fans out through a strategy. `tasks/check.py` enforces
this on the reusables and on every rendered workflow.

### pr

```
conform ─┐
         ├─► core / changes ─┬─► core / code  : lint ∥ audit ∥ test ─┬─► check/pr
detect ──┘                   └─► core / infra : validate ∥ plan     │
                  gateway / changes ─► gateway / code, gateway / infra … ┘ (skipped when unchanged)
```

`conform` and `detect` run in parallel. Each module has a small `<module> / changes` job
(`needs: [ conform, detect ]`, so a failing `conform` runs nothing) that publishes which sides
changed (`target` plays that role in the build). Each side is its own job calling `code.yml` or
`infra.yml`. GitHub draws one box per distinct set of `needs`, so the `code` lane needs only
that job and the `infra` lane needs it and `detect`: that is what keeps `core / code`,
`core / infra`, `checkout / code` and `checkout / infra` as four boxes in the graph instead of
one. `check / plan` is skipped on a pull request from a fork (it needs credentials).

### main

```
conform ─┐
detect ──┴─► split ──► build/core.2026-11-21.001, build/gateway.2026-11-21.001 …   (one tag per changed module)
```

`main` has no track and no `concurrency` (its single job reads `build / split` in the graph) (a cancelled pending run would lose its `before..HEAD`). `split`
computes the release name of every module `detect` reports as changed (a name is taken when the release tag
**or** its build tag `build/<name>` exists, locally or on the remote) and pushes the annotated build tag with
`GH_PIPELINES_TOKEN`, never forced: a rejected push takes the next number, up to 5 tries. A module that fails does
not stop the others; the job fails at the end naming it. No changed module is `nothing to build`.

### build

```
build/core.2026-11-21.001 ─► conform ─┐
                            target  ──┴─► build: reuse / code  ─► code  : lint ∥ audit ∥ test ─┬─► image ─► release
                                          reuse / infra ─► infra : validate ∥ plan     ┘
```

The run is named by its build tag, and `concurrency: build-<module>` with `cancel-in-progress: true` makes the
newest build of a module cancel the older one (`main` is linear and the next build covers its range). The build tag
of a run that was cancelled or failed stays.

- `target` reads the module from the tag, its directories and services from the registry, and the sides to check from
  `detect` over `last release..HEAD` (the newest release tag of the module that is an ancestor of the commit; without
  one, or on any error, both sides). A failed build is therefore re-checked by the next one.
- `reuse` asks whether the merged pull request already proved each check. It runs as two jobs, `reuse / code`
  (`check_prefix: <module> / code`) and `reuse / infra` (`check_prefix: <module> / infra`), so `code` and `infra`
  have different `needs` and the graph draws them in separate boxes. Reuse applies only when the last release is
  one first-parent commit behind HEAD (`target` answers `reuse`); otherwise every check runs. Each job queries GitHub check runs whose name
  starts with the prefix. A check counts as proved only when the pull request was green
  on it, the merge happened and every file of the merged commit has the blob the pull
  request tested. A doubt, an error or other content answers `false` and the check runs.
  It never compares shas: a squash or rebase merge writes a new commit. The result
  reaches the lanes as `skip_<check>`.
- `image` runs the `build` hook under the release name (it receives `TAG`, and `SENTRY_RELEASE=<sentry.project>@<TAG>` when the registry has the `sentry` key, empty otherwise) when no side failed. `release` publishes the
  release tag only when `image` succeeded (that push is the order to deploy staging, so a tag always has an image) and
  deletes the build tag; failing to delete it is a warning.
- A failing track never stops the others.

### deploy

```
conform ─┐
releases ┴─► core: preflight ─► apply ─┬─► deployment ─┬─► rollout ─► verify ─► record ─► notify
                                       └─► migrate ─┘
        record's rollback step = gh workflow run deploy.yml --ref <failed> -f environment=<env> -f rollback_to=<previous>
```

| event | environment | releases |
|---|---|---|
| push of a tag | `staging` | that tag, in the module its prefix names |
| dispatch on a tag | `staging` (default) or `production` | that tag, in the module its prefix names |
| dispatch on a branch | ❌ always fails — select a tag ref | — |

- `apply` runs only when it can matter: `preflight` runs `apply-needed`, which answers `false` only in staging, with a previous release recorded green, when the `infra` side of the module (infra dir and `shared` paths, documentation ignored) did not change between that release and this tag. Production, a first deploy, a re-run and any doubt answer `true`. When `apply` is skipped the jobs after it still run.
- `preflight` checks the tag shape, that it exists and that it points at the commit of the run.
  In production it also waits for the release to be recorded green in staging, polling for
  up to `staging_wait` seconds (default `600`; set via `inputs.staging_wait` in the dispatch).
  The preflight job has `timeout-minutes: 15`, which safely covers the default wait; lower it
  only when `staging_wait` is also lowered.
- The deploy never builds. A track per module runs in parallel, and the concurrency
  group `deploy-<module>-<environment>` never cancels.
- `migrate` and `rollout` are optional hooks that split the release in steps: `deployment` creates the new revisions without traffic, `migrate` runs the schema change in parallel with it, and `rollout` moves the traffic only after both passed, so the new code never serves against the old schema. A project that provides `rollout` must keep its `deployment` from moving traffic; a project without it keeps everything in `deployment`.
- The `rollback` step of `record` runs when `deployment`, `migrate`, `rollout` or `verify` failed, and only in a plain
  deploy (there is no `rollback` job). It writes its outcome to the job summary and dispatches
  `deploy.yml` on the failed ref with `rollback_to=<previous>` (the last release recorded green in the environment):
  the workflow is the failed ref's (already conformed) and the content is the previous release's, because every job checks
  out `inputs.tag`. Nothing is dispatched when there is no earlier release, or when a newer release of the module is queued
  for the environment (it is the fix forward and a dispatch would cancel it). A failed `apply` does not roll back: nothing went live.
- A rollback run is named `<env> · rollback · <P> (from <X>)`. `releases` validates `rollback_to` (a release of the same module as
  the ref) and exposes `rollback_of`; `preflight` runs `requirements` with `strict: false`, requires `<P>` recorded green in the
  environment and skips `apply`: a rollback swaps the revision (image and schema) and never touches the infrastructure, because the
  previous release's Terraform does not know what the failed release added and would destroy it; `record` and `notify` work as for any deploy (`rolled back` or
  `failed`). A rollback that fails never dispatches another.
- `record` runs when `apply` ran and records `success` (verify passed) or `failure`
  in GitHub Deployments, with `{module, tag}` (and `release_url` when `verify` wrote one) in the payload and the `url` from
  `verify`. Production reads those records; with `promote` on it reads the `promoted` environment instead of `staging`
  (`require_promoted`), and a manual dispatch passes `force: true` to fall back to the staging record
  (the run summary says `forced - promote skipped`).
- `notify` always runs: `ok`, `rolled back` or `failed`, in the run summary, as an annotation (`::error` for `failed`, `::notice`
  otherwise, shown at the top of the run page) and, when `NOTIFY_WEBHOOK_URL` is in the ward, on the webhook. A notification never reverts a deploy.
- On a `verify` failure `<code.dir>/tmp/artifacts` is uploaded as
  `verify-<module>-<environment>-<tag>`.

### promote

Generated only when the registry has the `promote` key.

```
workflow_dispatch(tag) ─► target ─► promote.yml: regression ∥ e2e ─┬─► promote ─┐
                                                                 └─► report ──┴─► notify
```

- The `record` job of `deploy` dispatches `promote.yml` with the `tag` input only after a staging deploy verified
  green (`promote_enabled`, not a rollback). A failed staging deploy dispatches nothing, so no promote run exists.
  `promote.yml` has no `workflow_run` trigger: `workflow_dispatch` is the only way in.
- The `incident` job lives in `deploy.yml` (reusable): with `promote_enabled`, when a production deploy has any
  failed job, it opens the Critical issue through `actions/critical` (`command: incident`).
- `target` reads the `tag` input, checks its shape and module, and takes the
  `release_url` from the green staging record; without one it fails with `verify wrote no release_url for <tag>`.
- `regression` and `e2e` run in parallel; the concurrency group `promote-<module>` cancels a run in progress.
- `promote` runs only when both passed, and the first match wins: `superseded` (the newest green release in staging is
  not this tag, or production already runs a newer one, compared as date then integer `NNN`), `capped` (`max_per_day`
  releases promoted in the last 24 hours) or `promoted`: it records a `promoted` deployment (payload `{module, tag}`)
  and dispatches `deploy.yml` on the tag with `environment=production`.
- `report` runs when a hook failed and opens (or comments on) the Critical issue
  `bug: <module> <hook> failed on <tag>`, labelled `urgency:critical` and `module:<m>`, plus `autofix:blocked` when a
  pull request labelled `autofix` was merged since the last promoted release. It uses `GH_PIPELINES_TOKEN`, so the
  `labeled` event starts workflows. The `incident` job of `deploy` does the same for a failed production deploy, always `autofix:blocked`.
- `regression` and `e2e` never see `GH_PIPELINES_TOKEN` or `secrets.ci.common`; `tasks/check.py` enforces it.
- `notify` reports `promoted`, `superseded`, `capped` or `failed`.

### The steps of a hook job

`checkout` → `secrets` (setup-ward) → `toolchain` (mise, in the side directory) →
`cache` (`<dir>/.ci-cache`, keyed by `mise.toml`, lockfiles and `go.sum`) →
`setup` (the project's action) → the hook. They are bundled in `actions/step`.
The project's `setup` action receives `dir`, `environment` and `step` (the hook name, e.g. `plan`
or `build`), so it can skip what a hook does not use, such as the cloud CLI for a plan. A project
action that does not declare `step` just ignores it.

## Sentry releases

Only with the `sentry` key in the registry. The name is `SENTRY_RELEASE = <sentry.project>@<release tag>`, for example
`has_warranty@core.2026-11-21.001`. A Sentry failure is a `::warning::sentry: …` with the step and the HTTP status; it never
fails the Build or the Deploy, and the token is masked before any call.

- The `release` job of the Build, after `stamp`, creates the release (`POST /api/0/organizations/{org}/releases/` with
  `version`, `projects` and `refs` carrying the repository and the commit of the tag) and finalizes it (`PUT` with
  `dateReleased`). The previous release of the project is the base of the commit range. Without the GitHub integration in
  Sentry the call is repeated without `refs` with a warning. A release that already exists counts as success.
- The `record` job of the Deploy, only with the `verify` green, marks the deploy (`POST …/releases/{version}/deploys/`
  with `environment`, `name` = the release tag, the verify `url`, `dateFinished`). A missing release (a Build older than the
  key) is created and the deploy is repeated once. A Rollback that records green is a Deploy of the destination tag, so it
  marks that release; a failed Deploy marks nothing.
- The run summary shows `Sentry release <version>: created|exists|failed` and `Sentry deploy <env>: marked|failed` with a link.
- The `build` hook is the bridge to the app: it passes `SENTRY_RELEASE` to the image (`--build-arg`) and the app uses it as the
  SDK `release`.

## Autofix

Only with the `autofix` key in the registry. `render.py` writes `autofix.yml` and, with `autofix.sentry`, `sentry-intake.yml`;
`conform` compares both and does not count them as extra workflows. Without the key the other workflows render byte for byte as before.

**`autofix.yml`** runs on `issues: labeled` and `workflow_dispatch(issue)`. Its job `autofix` runs only when the label is
`urgency:critical` (or on a dispatch) and calls the reusable `autofix.yml` with `vault`, `issue`, `event`, `sender`, `max_per_day`
and `modules` (`{"<m>":{"code":"<dir>","services":"<csv>"}}`). The concurrency group is `autofix-<issue>` with
`cancel-in-progress: false`, so two runs of one issue queue and different issues run in parallel.

```
select ─► fix ─► verify ─► publish
```

| job | secrets it sees | what it does |
|---|---|---|
| `select` | `GITHUB_TOKEN` with `contents: read`, `issues: write`, `pull-requests: read`, `actions: read` | validates the issue, dedups, applies the cap, resolves the module, writes the masked `.autofix/issue.json` (artifact `issue`); `issues: write` is for its refusal comments |
| `fix` | `<ns>:secrets.ci.agent` (`CLAUDE_CODE_OAUTH_TOKEN`), `<ns>:secrets.ci.test`, `<ns>:secrets.<m>.code.test` | runs Claude Code, writes `.autofix/result.json` and `.autofix/fix.patch` (artifact `autofix`) |
| `verify` | `<ns>:secrets.ci.test`, `<ns>:secrets.<m>.code.test` | clean checkout, scope, red, green, lint |
| `publish` | `<ns>:secrets.ci.common` (`GH_PIPELINES_TOKEN`, `NOTIFY_WEBHOOK_URL`) | branch, pull request and automerge, or a comment and a label; `notify` |

**Isolation.** `select`, `fix` and `verify` never see `GH_PIPELINES_TOKEN`, `SENTRY_AUTH_TOKEN` or `secrets.ci.common`. `fix` and
`verify` read their ward scopes with `export-key: 'false'`, so `WARD_KEY_<NS>` is not exported; every checkout uses
`persist-credentials: false`; `select`, `fix`, `verify` and `publish` declare `contents: read` (`select` adds `issues: write`,
`pull-requests: read` and `actions: read`). `agent.sh` fails with `agent environment leaks <name>` when `GH_PIPELINES_TOKEN`,
`SENTRY_AUTH_TOKEN`, `GITHUB_TOKEN` or a `WARD_KEY_*` is set, or the git remote carries a credential. `ci-hook` runs a copy of the
base `run/<step>` (or `ci/checks/<step>.sh`) for `lint` and `test` only, without `CLAUDE_CODE_OAUTH_TOKEN`. `tasks/check.py`
enforces these rules on the reusable. `export-key` isolates the key only when `br4zz4/setup-ward` supports the input; with an
older version the input is ignored and the key stays exported.

**Selection.** In order, each refusal ends `select` as `skipped` (a reason in the summary) or `rejected` (a comment too):
not an open `urgency:critical` issue; `autofix:blocked` → `blocked: needs a human`; the sender needs `write`, `maintain` or
`admin` (comment `[autofix] ignored: <login> cannot trigger the autofix`); exactly one `module:<m>` naming a module of the project
(comment `[autofix] rejected: missing module:<m> label` or `unknown module '<m>'`); a pull request with head `fix/issue-<n>` in any
state → `already attempted`; with `max_per_day > 0`, `autofix / fix` runs of the last 24 hours `>=` the cap → `daily cap
reached (<n>/<max>)`. A dispatch skips the last two. `issue.json` keeps `number`, `title`, `body`, `labels` and the 20 last comments
by `OWNER`, `MEMBER` or `COLLABORATOR`, every string masked; the body is cut at 20 000 characters and a comment at 4 000.

**Patch scope** (`actions/patch`, `scope`). The patch is refused when it is empty (`empty patch`), touches `.github/`, `.ward/`, a
`ci/` or `run/` directory, `mise.toml` or `<code_dir>/e2e/` (`forbidden path <file>`), touches a file outside `<code_dir>/`
(`outside module <file>`), or when `result.json` lists no regression test (`empty tests`) or a test that is not in the patch
(`test <file> not in patch`).

**Proof, red → green** (`verify`). The `tests` command applies only the regression tests of `result.json` and runs the `test` hook: it must
fail (`regression test passed before the fix` otherwise). The `full` command resets the checkout, applies the whole patch, and
`test` (`test failed with the fix`) and `lint` (`lint failed with the fix`) must pass. A pull request exists only after both.

**Outcomes** (`publish`, `if: always()` once `select` chose or rejected the issue):

| outcome | when | effect |
|---|---|---|
| `opened` | `verify` succeeded | pushes `fix/issue-<n>` with `GH_PIPELINES_TOKEN` (so `check/pr` starts), opens the pull request with the label `autofix` and `Fixes #<n>` against the ref of the run, enables `gh pr merge --auto --merge`, comments `[autofix] opened <pr url>` |
| `gave up` | the agent returned `gave_up` | comment `[autofix] gave up: <summary>`, label `autofix:failed` |
| `rejected` | `select` rejected the issue or `verify` refused the patch | comment `[autofix] rejected: <reason> (<run url>)`, label `autofix:failed` |
| `failed` | `fix` failed, timed out (30 minutes) or wrote no valid `result.json`, or `publish` errored | comment `[autofix] failed (<run url>)`, label `autofix:failed` |

**Automerge** needs "Allow auto-merge" in the repository settings and `check/pr` required by the ruleset of `main`. Without the
setting the pull request still opens and the comment becomes `[autofix] opened <pr url> (auto-merge unavailable: enable "Allow
auto-merge")`. The merge closes the issue through `Fixes #<n>`. `notify` runs `if: always()` with `kind: autofix` and the outcome.

**`sentry-intake.yml`** (with `autofix.sentry`) runs on the cron and `workflow_dispatch`, with the group `sentry-intake`, and has one job `intake`
that reads `<ns>:secrets.ci.common` and calls `actions/sentry` with `org`, `project` and `url` from the top-level `sentry`,
`environments` (csv), `min_events` and `modules`. It lists `GET {url}/api/0/organizations/{org}/issues/?project={project}` (unresolved,
`level:[error,fatal]`, `firstSeen:-24h`, `times_seen:>=min_events`, `sort=freq`) and opens at most **5** Critical issues per run, most
frequent first. The module is the first part of the `release` of the latest event; a release naming no module gets the note
`[intake] skipped: release '<release>' names no module`. The issue is `bug: <SHORT-ID> <title>` (80 characters) labelled `urgency:critical`,
`module:<m>` and `sentry`, opened with `GH_PIPELINES_TOKEN` so the `labeled` event starts the autofix.

- **PII allow-list.** Only the issue fields `shortId`, `title`, `culprit`, `level`, `platform`, `count`, `firstSeen`, `lastSeen`; the event `release`,
  `environment`, the tags `transaction`, `handled`, `mechanism`, `level`, `runtime`, `runtime.name`; exceptions (`type`, masked `value`, `mechanism.type`, frames with
  `filename`, `module`, `function`, `lineno`, `colno`, `in_app` and the source context lines); the last 30 breadcrumbs
  (`timestamp`, `category`, `level`, `message`). `user`, `ip_address`, `cookies`, `headers`, `request.data` and frame `vars` never
  reach the issue, and every string goes through the same `mask` as the `critical` action (e-mails become `<email>`).
- **Dedup.** The Sentry issue is skipped when a GitHub issue, open or closed, already carries its short id in the title, or when a
  note starting with `[intake]` is there. The GitHub check is the reliable one.
- **Note, best effort.** The note `[intake] #<n> <url>` on the Sentry issue needs a token allowed to comment; an organization
  token gets a `403`, which is only a warning. Do not rely on it.
- No candidate: `nothing to intake` in the summary.

Ward: `SENTRY_AUTH_TOKEN` and `GH_PIPELINES_TOKEN` live in `<ns>:secrets.ci.common`; `CLAUDE_CODE_OAUTH_TOKEN` in `<ns>:secrets.ci.agent`. The test scopes
hold only test values.

## Gate — `check/pr`

The generated `pr.yml` ends with a job whose name is exactly `check/pr`:
`if: always()`, `needs` every other job, no reusable. It fails when any needed job
`failed` or was `cancelled`; `skipped` passes. It exists because a pull request that
touches no module skips every track, and a check that is never created blocks a
merge forever. `check/pr` is the only status check a project's ruleset requires.
It is the one declared exception to the `<module> / <job>` naming.

## Conform

First job of every run. It renders the workflows from the registry and the ward
config and compares them with the committed ones. It fails when:

- a generated workflow differs from the render;
- `.github/workflows/` holds a file outside `pr`, `main`, `build`, `deploy` and `extra_workflows`;
- a restricted ward key is mentioned outside `deploy.yml`;
- a module lacks a hook, has a script outside the vocabulary or has no `mise.toml`;
- `.github/actions/setup/action.yml` is missing;
- the ward config does not declare one project namespace: its default vault (or `<ns>::default`),
  with the `::restricted` pair when there is one (the pair is optional; without it the
  production deploy stops in `preflight`);
- a module asks for a service outside the catalog.

Modes: `fix` (pull requests from the repository itself, where the key is
available) writes the render, commits `ci: render workflows` to the branch and
fails so the next run starts on the new commit; `check` (main, deploy, forks)
only fails and writes the expected diff to the run summary. `render.py` and
`conform.py` use only the Python standard library and run the same on macOS and Linux.

## Secrets

The ward is the source of truth. GitHub holds `WARD_KEY_<NS>` and
`WARD_KEY_<NS>_RESTRICTED`; everything else is read from the vaults.

| who | scopes |
|---|---|
| conform (fix), tag, notify | `<ns>:secrets.ci.common` — `GH_PIPELINES_TOKEN`, `NOTIFY_WEBHOOK_URL` |
| Sentry release and deploy marks | `<ns>:secrets.ci.common` — `SENTRY_AUTH_TOKEN`, an Internal Integration (or organization) token with `project:releases` and `org:read`; missing only warns |
| Autofix `publish` and the Sentry intake | `<ns>:secrets.ci.common` — `GH_PIPELINES_TOKEN`, `SENTRY_AUTH_TOKEN` (the intake; needs `project:read` and `event:read`) |
| Autofix `fix` | `<ns>:secrets.ci.agent` — `CLAUDE_CODE_OAUTH_TOKEN`, plus the test scopes, read with `export-key: 'false'` |
| jobs in `test` / `staging` | `<ns>:secrets.ci.<env>` and `<ns>:secrets.<m>.<code\|infra>.<env>` |
| jobs in `production` | `<ns>::restricted:secrets.ci.production` and `<ns>::restricted:secrets.<m>.<code\|infra>.production` |

- `secrets.ci.<env>` holds what the project's `setup` action needs to authenticate.
- The restricted key reaches only the module jobs of `deploy.yml`, and only on
  a dispatch. Inside the reusable it is read only when `environment == 'production'`.
  conform rejects any other mention.
- Only the jobs of the `deploy.yml` reusable use `environment:`, and only as
  `${{ inputs.environment == 'production' && 'production' || 'staging' }}`, so every other deploy runs in
  `staging`. The secrets of an `environment:` are not visible inside a reusable workflow, so the caller
  `deploy.yml` passes the restricted key as `WARD_KEY_RESTRICTED` (from the repository secret
  `WARD_KEY_<NS>_RESTRICTED`); the reusable reads it only when `environment == 'production'`. Rendered
  workflows never use `environment:`.
- `br4zz4/setup-ward@v1` installs ward and exports the values of the scopes to the
  job, masked, along with the keys themselves. An empty scope is a notice, not an error.
- `GITHUB_TOKEN` permissions are declared by the generated workflows: `contents: read`
  and `id-token: write`, `checks: read` and `pull-requests: read` on build for `reuse`,
  `deployments: write` and `actions: write` on deploy for `record` and the rollback dispatch. The release tag is pushed with
  `GH_PIPELINES_TOKEN`, a PAT with the `workflow` scope, because a tag pushed with
  `GITHUB_TOKEN` does not start workflows.

## Tags

`<module>.YYYY-MM-DD.NNN`, for example `core.2026-11-15.001`.

- The module is the prefix: `${TAG%%.*}`. The tag alone says what to deploy.
- The day is `America/Sao_Paulo`; `NNN` is the day's count for the module plus one,
  zero-padded to three digits and growing past three when needed.
- Release tags are annotated, `release <tag>`, named by `split` (as the build tag `build/<tag>`) and published by the `release` job of the build after the image was built.
- Only this shape is a release. `preflight` rejects a tag that does not point at the
  commit of the run: a release is a commit already built, never a tag moved later.

## Detection

`detect` reads the event's change set:

| event | change set |
|---|---|
| `push` | `before..HEAD`; without a usable before or `HEAD^`, everything |
| `pull_request` | `merge-base(base)..HEAD` |
| any other event | everything |

`modules/<m>/code/**` touches the code side of `<m>`, `modules/<m>/infra/**` the
infra side, a `shared` path touches every module and unrelated paths touch nothing.
Documentation never counts: `*.md`, `docs/` and `.project/docs/` are dropped from the
change set first, so a documentation-only change touches no module (no checks, build or deploy).
The single output is `changes`:
`{"core": {"any": true, "code": true, "infra": false}, ...}` with every module of
the registry, read as `fromJSON(needs.detect.outputs.changes).core.any`.

## Limits

- **Nesting:** the project workflow calls a reusable, which calls actions: well under
  GitHub's limit.
- A job-level `if` reads only `github`, `needs`, `inputs` and `vars`.
- Relative `uses:` resolve against the caller's repository, so internal references are
  absolute (`br4zz4/pipelines/...@v2`). The one exception is `./.github/actions/setup`,
  which must resolve in the project.
- A reusable workflow cannot read `secrets` in a composite action, so actions take
  tokens as inputs.
- The pipelines are platform-agnostic: workflows and actions never name a provider.
  `tasks/check.py` enforces it, together with the naming rules, the closed workflow
  set and the retired names.
- `examples/` is static documentation; a project copies and owns what it needs.
- **Versioning:** the published tag is `v2`. The format of the generated workflows
  does not change inside `v2`; a change to it is a new major version. `v1` is frozen at its last commit with no
  maintenance branch: a project migrates by regenerating with `--ref v2` and deleting `ci/deploy/rollback.sh`
  (and its `rollback=` output). A dispatch on a tag from before the migration runs the `deploy.yml` of that tag.
