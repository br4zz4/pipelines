# Contract

What a repository must provide for `br4zz4/pipelines@v2` to run it, and what the
pipelines guarantee in return. Everything is convention plus one file:
`.github/modules.json`.

## Files of a project

```
.github/modules.json                  the registry — the only file edited by hand
.github/actions/setup/action.yml      authentication and system packages; never a language
.github/workflows/{pr,main,build,deploy}.yml   GENERATED by conform
.ward/config.yaml                     vaults <ns> (or <ns>::default) and <ns>::restricted
.ward/vaults/**                       encrypted, committed
modules/<m>/code/mise.toml            toolchain of the code side
modules/<m>/code/run/{lint,audit,test}       preferred; same script runs locally in the container and in CI
modules/<m>/code/ci/checks/{lint,audit,test}.sh   still accepted when run/<step> is absent
modules/<m>/code/ci/checks/build.sh
modules/<m>/infra/mise.toml           toolchain of the infra side
modules/<m>/infra/ci/checks/{validate,plan}.sh
modules/<m>/infra/ci/deploy/{apply,deployment,migrate,rollout,verify}.sh
```

## Registry — `.github/modules.json`

```json
{
  "shared": [".github/", ".ward/", "Makefile"],
  "extra_workflows": ["cleanup.yml"],
  "modules": {
    "core":    { "services": ["postgres"] },
    "gateway": {},
    "events":  { "services": ["postgres", "redis"], "code": { "dir": "modules/events/app" } }
  }
}
```

| key | meaning |
|---|---|
| `shared` | paths that count as a change for every module |
| `extra_workflows` | files allowed next to `pr`, `main`, `build` and `deploy` in `.github/workflows/`; default `[]` |
| `modules.<m>.services` | subset of `postgres` and `redis`; only `<module> / code / test` starts them (`build / code / test` too; `deploy / verify` runs without services) |
| `modules.<m>.code.dir`, `modules.<m>.infra.dir` | default `modules/<m>/code` and `modules/<m>/infra` |

A module name matches `[a-z][a-z0-9_]*`: it is the tag prefix and a job id. The
project namespace `<ns>` is read from `.ward/config.yaml`; the GitHub secrets are
`WARD_KEY_<NS>` and `WARD_KEY_<NS>_RESTRICTED` with `<NS>` upper-cased the way
ward derives it (`has_warranty` → `WARD_KEY_HAS_WARRANTY`).

## Hooks — a closed vocabulary

| side | hook | job (GitHub UI) | ward environment |
|---|---|---|---|
| code | `lint`, `audit`, `test` | `<module> / code / lint`, `… / audit`, `… / test` | `test` |
| code | `build` | `<module> / code / build` (main only) | `staging` |
| infra | `validate` | `<module> / infra / validate` | `test` |
| infra | `plan` | `<module> / infra / plan` | `staging` |
| infra | `apply`, `deployment`, `verify` | `deploy / apply`, `… / deployment`, `… / verify` | `staging` or `production` |
| infra | `migrate`, `rollout` (optional) | `deploy / migrate`, `… / rollout` | `staging` or `production` |

- **Every hook is mandatory, except `migrate` and `rollout`.** Those two are optional: without the script the job prints `skipping` and passes, so a project whose `deployment` does everything keeps working.
- **Every other hook is mandatory.** A missing script fails the step
  (`::error::missing ci/checks/<hook>.sh`, or `missing run/<hook> or ci/checks/<hook>.sh` for lint/audit/test, or `ci/deploy/<hook>.sh`). A module with nothing to do keeps a script
  that prints why and exits 0.
- A `ci/<context>/*.sh` outside the table is rejected by conform. Helpers live next to the
  hooks (for example `lib/`), never in `ci/`.
- A hook runs with its side directory as the working directory and receives
  `MODULE`, `ENVIRONMENT`, `TAG`, `PREVIOUS_TAG` (deploy hooks: the last release recorded green in the environment, empty when there is none) and `CI_CACHE_DIR` (`<dir>/.ci-cache`, restored
  by the cache step) plus the values of its ward scope.
- `chmod +x` is neither required nor trusted: a non-executable script runs with `sh`.
- `verify` writes `url=<url>` to `$GITHUB_OUTPUT`. There is no `rollback` hook and no rollback
  point (retired in v2): a failed deploy dispatches a deploy of the previous release.
  conform rejects a leftover `ci/deploy/rollback.sh`.
- The hook is the implementation. `make <module>.<step>` from `br4zz4/commons` runs the
  same script locally, with the same working directory and variables.

## Workflows

Each side of each module is a literal job of the project workflow that calls a reusable
workflow (`code.yml`, `infra.yml`, `deploy.yml`); the jobs of the reusable have literal names,
so the graph reads `<module> / <side> / <job>`. No `name:` holds an expression, every step is named, only the jobs of the `deploy.yml` reusable use `environment:` (and only as `${{ inputs.environment == 'production' && 'production' || 'staging' }}`) and no job fans out through a strategy. `tasks/check.py` enforces
this on the reusables and on every rendered workflow.

### pr

```
conform ─┐
         ├─► core / changes ─┬─► core / code  : lint ∥ audit ∥ test ─┬─► check/pr
detect ──┘                   └─► core / infra : validate ∥ plan     │
                  gateway / changes ─► gateway / code, gateway / infra … ┘ (skipped when unchanged)
```

`conform` and `detect` run in parallel. Each module has a small `<module> / changes` job
(`needs: [ conform, detect ]`, so a failing `conform` runs nothing) that publishes which sides
changed (`target` plays that role in the build). Each side is its own job calling `code.yml` or
`infra.yml`. GitHub draws one box per distinct set of `needs`, so the `code` lane needs only
that job and the `infra` lane needs it and `detect`: that is what keeps `core / code`,
`core / infra`, `checkout / code` and `checkout / infra` as four boxes in the graph instead of
one. `check / plan` is skipped on a pull request from a fork (it needs credentials).

### main

```
conform ─┐
detect ──┴─► split ──► build/core.2026-11-21.001, build/gateway.2026-11-21.001 …   (one tag per changed module)
```

`main` has no track and no `concurrency` (a cancelled pending run would lose its `before..HEAD`). `split`
computes the release name of every module `detect` reports as changed (a name is taken when the release tag
**or** its build tag `build/<name>` exists, locally or on the remote) and pushes the annotated build tag with
`GH_PIPELINES_TOKEN`, never forced: a rejected push takes the next number, up to 5 tries. A module that fails does
not stop the others; the job fails at the end naming it. No changed module is `nothing to build`.

### build

```
build/core.2026-11-21.001 ─► conform ─┐
                            target  ──┴─► build: reuse ─┬─► code  : lint ∥ audit ∥ test ─┬─► image ─► release
                                                        └─► infra : validate ∥ plan     ┘
```

The run is named by its build tag, and `concurrency: build-<module>` with `cancel-in-progress: true` makes the
newest build of a module cancel the older one (`main` is linear and the next build covers its range). The build tag
of a run that was cancelled or failed stays.

- `target` reads the module from the tag, its directories and services from the registry, and the sides to check from
  `detect` over `last release..HEAD` (the newest release tag of the module that is an ancestor of the commit; without
  one, or on any error, both sides). A failed build is therefore re-checked by the next one.
- `reuse` asks whether the merged pull request already proved each check. It runs two
  steps: `reuse-code` with `check_prefix: <module> / code` and `reuse-infra` with
  `check_prefix: <module> / infra`. Each step queries GitHub check runs whose name
  starts with the prefix. A check counts as proved only when the pull request was green
  on it, the merge happened and every file of the merged commit has the blob the pull
  request tested. A doubt, an error or other content answers `false` and the check runs.
  It never compares shas: a squash or rebase merge writes a new commit. The result
  reaches the lanes as `skip_<check>`.
- `image` runs the `build` hook under the release name (it receives `TAG`) when no side failed. `release` publishes the
  release tag only when `image` succeeded (that push is the order to deploy staging, so a tag always has an image) and
  deletes the build tag; failing to delete it is a warning.
- A failing track never stops the others.

### deploy

```
conform ─┐
releases ┴─► core: preflight ─► apply ─┬─► deployment ─┬─► rollout ─► verify ─┬─► record ─┐
                                       └─► migrate ─┘                      └─► rollback ┴─► notify
        rollback = gh workflow run deploy.yml --ref <failed> -f environment=<env> -f rollback_to=<previous>
```

| event | environment | releases |
|---|---|---|
| push of a tag | `staging` | that tag, in the module its prefix names |
| dispatch on a tag | `staging` (default) or `production` | that tag, in the module its prefix names |
| dispatch on a branch | ❌ always fails — select a tag ref | — |

- `apply` runs only when it can matter: `preflight` runs `apply-needed`, which answers `false` only in staging, with a previous release recorded green, when the `infra` side of the module (infra dir and `shared` paths, documentation ignored) did not change between that release and this tag. Production, a first deploy, a re-run and any doubt answer `true`. When `apply` is skipped the jobs after it still run.
- `preflight` checks the tag shape, that it exists and that it points at the commit of the run.
  In production it also waits for the release to be recorded green in staging, polling for
  up to `staging_wait` seconds (default `600`; set via `inputs.staging_wait` in the dispatch).
  The preflight job has `timeout-minutes: 15`, which safely covers the default wait; lower it
  only when `staging_wait` is also lowered.
- The deploy never builds. A track per module runs in parallel, and the concurrency
  group `deploy-<module>-<environment>` never cancels.
- `migrate` and `rollout` are optional hooks that split the release in steps: `deployment` creates the new revisions without traffic, `migrate` runs the schema change in parallel with it, and `rollout` moves the traffic only after both passed, so the new code never serves against the old schema. A project that provides `rollout` must keep its `deployment` from moving traffic; a project without it keeps everything in `deployment`.
- `rollback` runs when `deployment`, `migrate`, `rollout` or `verify` failed, and only in a plain deploy. It dispatches
  `deploy.yml` on the failed ref with `rollback_to=<previous>` (the last release recorded green in the environment):
  the workflow is the failed ref's (already conformed) and the content is the previous release's, because every job checks
  out `inputs.tag`. Nothing is dispatched when there is no earlier release, or when a newer release of the module is queued
  for the environment (it is the fix forward and a dispatch would cancel it). A failed `apply` does not roll back: nothing went live.
- A rollback run is named `<env> · rollback · <P> (from <X>)`. `releases` validates `rollback_to` (a release of the same module as
  the ref) and exposes `rollback_of`; `preflight` runs `requirements` with `strict: false`, requires `<P>` recorded green in the
  environment and forces `apply` (`apply-needed` answers `true`); `record` and `notify` work as for any deploy (`rolled back` or
  `failed`). A rollback that fails never dispatches another.
- `record` runs when `apply` ran and records `success` (verify passed) or `failure`
  in GitHub Deployments, with `{module, tag}` in the payload and the `url` from
  `verify`. Production reads those records.
- `notify` always runs: `ok`, `rolled back` or `failed`, in the run summary and, when
  `NOTIFY_WEBHOOK_URL` is in the ward, on the webhook. A notification never reverts a deploy.
- On a `verify` failure `<code.dir>/tmp/artifacts` is uploaded as
  `verify-<module>-<environment>-<tag>`.

### The steps of a hook job

`checkout` → `secrets` (setup-ward) → `toolchain` (mise, in the side directory) →
`cache` (`<dir>/.ci-cache`, keyed by `mise.toml`, lockfiles and `go.sum`) →
`setup` (the project's action) → the hook. They are bundled in `actions/step`.
The project's `setup` action receives `dir`, `environment` and `step` (the hook name, e.g. `plan`
or `build`), so it can skip what a hook does not use, such as the cloud CLI for a plan. A project
action that does not declare `step` just ignores it.

## Gate — `check/pr`

The generated `pr.yml` ends with a job whose name is exactly `check/pr`:
`if: always()`, `needs` every other job, no reusable. It fails when any needed job
`failed` or was `cancelled`; `skipped` passes. It exists because a pull request that
touches no module skips every track, and a check that is never created blocks a
merge forever. `check/pr` is the only status check a project's ruleset requires.
It is the one declared exception to the `<module> / <job>` naming.

## Conform

First job of every run. It renders the workflows from the registry and the ward
config and compares them with the committed ones. It fails when:

- a generated workflow differs from the render;
- `.github/workflows/` holds a file outside `pr`, `main`, `build`, `deploy` and `extra_workflows`;
- a restricted ward key is mentioned outside `deploy.yml`;
- a module lacks a hook, has a script outside the vocabulary or has no `mise.toml`;
- `.github/actions/setup/action.yml` is missing;
- the ward config does not declare one project namespace: its default vault (or `<ns>::default`),
  with the `::restricted` pair when there is one (the pair is optional; without it the
  production deploy stops in `preflight`);
- a module asks for a service outside the catalog.

Modes: `fix` (pull requests from the repository itself, where the key is
available) writes the render, commits `ci: render workflows` to the branch and
fails so the next run starts on the new commit; `check` (main, deploy, forks)
only fails and writes the expected diff to the run summary. `render.py` and
`conform.py` use only the Python standard library and run the same on macOS and Linux.

## Secrets

The ward is the source of truth. GitHub holds `WARD_KEY_<NS>` and
`WARD_KEY_<NS>_RESTRICTED`; everything else is read from the vaults.

| who | scopes |
|---|---|
| conform (fix), tag, notify | `<ns>:secrets.ci.common` — `GH_PIPELINES_TOKEN`, `NOTIFY_WEBHOOK_URL` |
| jobs in `test` / `staging` | `<ns>:secrets.ci.<env>` and `<ns>:secrets.<m>.<code\|infra>.<env>` |
| jobs in `production` | `<ns>::restricted:secrets.ci.production` and `<ns>::restricted:secrets.<m>.<code\|infra>.production` |

- `secrets.ci.<env>` holds what the project's `setup` action needs to authenticate.
- The restricted key reaches only the module jobs of `deploy.yml`, and only on
  a dispatch. Inside the reusable it is read only when `environment == 'production'`.
  conform rejects any other mention.
- Only the jobs of the `deploy.yml` reusable use `environment:`, and only as
  `${{ inputs.environment == 'production' && 'production' || 'staging' }}`, so every other deploy runs in
  `staging`. This lets the project keep the production key only in the `production`
  environment; the project names the secret in `production_key_secret` (default
  `WARD_KEY_<vault>_RESTRICTED`). Rendered workflows never use `environment:`.
- `br4zz4/setup-ward@v1` installs ward and exports the values of the scopes to the
  job, masked, along with the keys themselves. An empty scope is a notice, not an error.
- `GITHUB_TOKEN` permissions are declared by the generated workflows: `contents: read`
  and `id-token: write`, `checks: read` and `pull-requests: read` on build for `reuse`,
  `deployments: write` and `actions: write` on deploy for `record` and the rollback dispatch. The release tag is pushed with
  `GH_PIPELINES_TOKEN`, a PAT with the `workflow` scope, because a tag pushed with
  `GITHUB_TOKEN` does not start workflows.

## Tags

`<module>.YYYY-MM-DD.NNN`, for example `core.2026-11-15.001`.

- The module is the prefix: `${TAG%%.*}`. The tag alone says what to deploy.
- The day is `America/Sao_Paulo`; `NNN` is the day's count for the module plus one,
  zero-padded to three digits and growing past three when needed.
- Release tags are annotated, `release <tag>`, named by `split` (as the build tag `build/<tag>`) and published by the `release` job of the build after the image was built.
- Only this shape is a release. `preflight` rejects a tag that does not point at the
  commit of the run: a release is a commit already built, never a tag moved later.

## Detection

`detect` reads the event's change set:

| event | change set |
|---|---|
| `push` | `before..HEAD`; without a usable before or `HEAD^`, everything |
| `pull_request` | `merge-base(base)..HEAD` |
| any other event | everything |

`modules/<m>/code/**` touches the code side of `<m>`, `modules/<m>/infra/**` the
infra side, a `shared` path touches every module and unrelated paths touch nothing.
Documentation never counts: `*.md`, `docs/` and `.project/docs/` are dropped from the
change set first, so a documentation-only change touches no module (no checks, build or deploy).
The single output is `changes`:
`{"core": {"any": true, "code": true, "infra": false}, ...}` with every module of
the registry, read as `fromJSON(needs.detect.outputs.changes).core.any`.

## Limits

- **Nesting:** the project workflow calls a reusable, which calls actions: well under
  GitHub's limit.
- A job-level `if` reads only `github`, `needs`, `inputs` and `vars`.
- Relative `uses:` resolve against the caller's repository, so internal references are
  absolute (`br4zz4/pipelines/...@v2`). The one exception is `./.github/actions/setup`,
  which must resolve in the project.
- A reusable workflow cannot read `secrets` in a composite action, so actions take
  tokens as inputs.
- The pipelines are platform-agnostic: workflows and actions never name a provider.
  `tasks/check.py` enforces it, together with the naming rules, the closed workflow
  set and the retired names.
- `examples/` is static documentation; a project copies and owns what it needs.
- **Versioning:** the published tag is `v2`. The format of the generated workflows
  does not change inside `v2`; a change to it is a new major version. `v1` is frozen at its last commit with no
  maintenance branch: a project migrates by regenerating with `--ref v2` and deleting `ci/deploy/rollback.sh`
  (and its `rollback=` output). A dispatch on a tag from before the migration runs the `deploy.yml` of that tag.
